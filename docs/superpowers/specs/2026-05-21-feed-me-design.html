Design Spec — v1.0

Feed Me

A personal podcast feed of AI-narrated articles · 2026-05-21

Feed Me is a service that turns saved articles into a personal podcast feed. You share a URL via the iOS Share Sheet; within ~60 seconds an AI-narrated episode appears in the podcast app of your choice. Architected for personal use first, with a clear path to multi-user public product later.

1. Goals & non-goals

Goals

  • Share any URL from any iOS app and have an audio episode in your podcast app within ~60 seconds.
  • Listen in the podcast app of your choice (Apple Podcasts, Overcast, Pocket Casts, etc.) via a standard RSS feed.
  • Each user gets a personal, unguessable feed URL; new submissions append episodes.
  • Audio is a faithful, lightly-formatted read of the article — no editorializing, no host persona.
  • Cheap, simple to operate, and reliable for personal use; architected so going public later is incremental work, not a rewrite.

Non-goals (v1)

  • No PDF, file, or arbitrary text input — URLs only.
  • No in-app player. We produce an RSS feed and audio files; listening UX is delegated to existing podcast apps.
  • No web/Android/Mac client. iOS Share Sheet only.
  • No summarization, discussion, multi-host, or AI commentary.
  • No multi-voice per feed, no per-episode voice override.
  • No search, transcripts, social sharing, or analytics.

2. User flows

2.1 First-time setup (web, ~2 minutes)

  1. Open the Feed Me site on your iPhone, tap Sign in, enter your password (set during deploy via env var). A signed session cookie keeps you logged in.
  2. On the settings page, tap Add to Apple Podcasts (or copy the feed URL into another podcast app). This opens Apple Podcasts to your feed with a one-tap Follow button.
  3. Tap Install Shortcut. This opens the canonical, iCloud-signed Feed Me shortcut in the Shortcuts app — tap Get Shortcut to add it. The first time the shortcut runs (or when you tap "Run on first install"), it prompts for your API token; copy it from the settings page and paste it once. iOS stores the token inside the shortcut for all future runs.
  4. Pick a voice (default: shimmer) and you're done.

The settings page is the single source of truth for your feed URL, API token, voice, and saved-episode history. Tokens can be rotated from this page if the phone is lost or compromised — after rotating, open the shortcut, run the embedded Reset Token action, and paste the new value.

Why not a one-tap install with the token pre-embedded? iOS blocks unsigned .shortcut files by default (the "Allow Untrusted Shortcuts" toggle is even hidden until a user has installed at least one shortcut). The smooth install path requires an iCloud-signed shortcut, and Apple signs those through the Shortcuts app — they can't be generated server-side with a per-user token baked in. Every comparable tool (Readwise, Matter, Snipd) ships the same "install signed shortcut, paste token once" UX.

2.2 Saving an article

  1. In Safari (or any iOS app), tap Share → Send to Feed Me.
  2. The Shortcut POSTs the URL to the API; you see a brief success toast.
  3. ~30–90 seconds later, the new episode appears in your podcast app on next refresh.

2.3 Listening

Standard podcast app behavior. Newest episode at the top of the feed. Your podcast app handles downloads, playback position, speed, and local cleanup.

Supported apps (subscribe by URL): Apple Podcasts, Overcast, Pocket Casts, Castro, AntennaPod, Podverse, Podcast Addict, and most other RSS-aware players.

Not supported: Spotify. Spotify's consumer app does not let listeners subscribe to arbitrary RSS feed URLs, and its "private podcast" tooling is enterprise-only. Workarounds (submitting your feed to Spotify for Podcasters with an obscure name) make the feed publicly indexed, which defeats the point. Documented as a non-goal in §13.

3. Architecture

One Fly.io machine runs a single Node.js process. Three HTTP surfaces (settings UI, ingest API, RSS feed), one in-process worker loop. SQLite (on a Fly volume) holds all state including sessions. Cloudflare R2 serves MP3 audio over its default *.r2.dev hostname. Two vendors, one log stream.

4. Processing pipeline

Each ingested URL becomes one episodes row with status='pending'. The worker loop wakes every 5 seconds, claims one pending episode (compare-and-swap to processing), and runs the four steps below in sequence. On any failure the episode is marked failed with an error_message. Whole-pipeline retry happens up to 3 times via the row's attempts counter — step-level retry would be a nice-to-have but isn't worth a separate jobs table at this scale.

1extract (with Wayback fallback)~3–8s

HTTP GET the URL with a real-browser User-Agent. Run Mozilla Readability on the HTML to capture title, byline, siteName, and clean article text. If the result trips the paywall heuristic (§5), call the Wayback Availability API and re-run Readability on the latest snapshot. If word count exceeds 20,000 either before or after the Wayback retry, fail with "Article too long (over 20k words)." If extraction still fails after Wayback, fail with "Couldn't extract article."

2build script<50ms

Template-only, no LLM: "From {siteName}{byline ? ', by ' + byline : ''}. {title}.\n\n{body}". Body is the Readability plain text. Normalize whitespace; preserve paragraph breaks so TTS pacing sounds natural.

3TTS (chunked)~20–90s

OpenAI TTS has historically had a ~4,096-character per-request limit on tts-1; the newer gpt-4o-mini-tts may differ — verify in the current API docs before implementation. If the limit holds, split the script on paragraph boundaries into chunks of ≤ 3,800 characters (safety margin) and call the TTS endpoint with the user's voice; chunks run with a small concurrency limit (e.g. 3) to respect rate limits.

MP3 frames are independent, but each response includes an ID3 header. Naive cat-style concatenation stacks N ID3 tags into the output, which a handful of players (notably some Apple Podcasts versions) reject. Strip ID3 from chunks 2..N before concatenating — ~10 lines with node-id3, no ffmpeg needed.

4upload~1–3s

PUT the combined MP3 to R2 at key audio/{user_id}/{audio_token}.mp3, where audio_token is a per-episode random base64url string (16 bytes). Read Content-Length for audio_size_bytes; estimate duration_seconds from byte length and bitrate. Mark episode: status='ready', ready_at=now(), store audio_token. The RSS feed picks up the new episode on next request.

5. Paywall handling

The Wayback fallback is a control-flow detail of step 1, triggered when either heuristic fires on the direct fetch:

  • Length signal: extracted body has fewer than 200 words.
  • Phrase signal: body contains one of "subscribe to continue", "sign in to read", "this article is for subscribers", "create a free account", or "premium content", plus a small denylist of known paywall banners.

Either signal sends the URL through the Wayback Availability API. The fallback is ethical (it uses the Internet Archive's official API, not scraped clones), but coverage is imperfect — articles published in the last 24 hours often aren't archived yet.

Known limitation: when both the direct fetch and Wayback fail, the episode is marked failed. A future "Paste text" Shortcut variant (in backlog) covers paywalled content not in Wayback.

6. Data model

SQLite, three tables. Times are unix epoch milliseconds. No public IDs or UUIDs — the random feed_token (per user), audio_token (per episode), and session_token (per login) double as both credential and URL slug.

CREATE TABLE users (
  id                INTEGER PRIMARY KEY,
  email             TEXT NOT NULL,
  password_hash     TEXT NOT NULL,         -- bcrypt(SETTINGS_PASSWORD) seeded on first run
  voice             TEXT NOT NULL DEFAULT 'shimmer',
  feed_token        TEXT NOT NULL UNIQUE,  -- 32 random bytes, base64url, used in feed URL
  api_token_hash    TEXT NOT NULL,         -- sha256 of bearer token; plaintext never stored
  created_at        INTEGER NOT NULL
);

CREATE TABLE episodes (
  id                INTEGER PRIMARY KEY,
  user_id           INTEGER NOT NULL REFERENCES users(id),
  url               TEXT NOT NULL,
  url_hash          TEXT NOT NULL,         -- sha256(user_id || normalized_url), for dedup
  status            TEXT NOT NULL,         -- pending | processing | ready | failed
  attempts          INTEGER NOT NULL DEFAULT 0,
  title             TEXT,
  byline            TEXT,
  site_name         TEXT,
  word_count        INTEGER,
  audio_token       TEXT,                  -- 16 random bytes, base64url; slugs the R2 key + RSS guid
  audio_size_bytes  INTEGER,
  duration_seconds  INTEGER,
  error_message     TEXT,
  created_at        INTEGER NOT NULL,
  updated_at        INTEGER NOT NULL,
  ready_at          INTEGER,
  UNIQUE(user_id, url_hash)
);

CREATE TABLE sessions (
  token             TEXT PRIMARY KEY,      -- 32 random bytes, base64url; stored in cookie
  user_id           INTEGER NOT NULL REFERENCES users(id),
  created_at        INTEGER NOT NULL,
  expires_at        INTEGER NOT NULL,      -- created_at + 30 days
  last_seen_at      INTEGER NOT NULL
);

CREATE INDEX idx_episodes_pending      ON episodes(status, updated_at) WHERE status IN ('pending','processing');
CREATE INDEX idx_episodes_user_ready   ON episodes(user_id, ready_at DESC) WHERE status = 'ready';
CREATE INDEX idx_sessions_user_expires ON sessions(user_id, expires_at);

Crash recovery: on startup the app runs UPDATE episodes SET status='pending' WHERE status='processing' AND updated_at < now() - 5min — sweeps stuck rows back into the queue without a separate jobs table.

7. API contracts

GET /, /login, POST /login public

Server-rendered HTML. Root redirects to /settings if a valid session cookie is present, otherwise /login. The login page is a single email + password form. On submit, the server checks bcrypt, creates a sessions row, and sets an HttpOnly; Secure; SameSite=Lax cookie with the session token (30-day expiry, sliding on activity).

GET /settings, POST /settings/voice, POST /settings/rotate-token session

Single page showing:

  • Feed URL with one-tap copy + an "Add to Apple Podcasts" button that opens podcast://<feed_url>.
  • Install Shortcut button linking to /shortcut.shortcut.
  • Voice picker (radio buttons; submits to POST /settings/voice).
  • Rotate API token button (invalidates the old token, redirects to settings with new value visible once).
  • Recent episodes — last 30 rows, including failed ones with error_message visible.

Shortcut install (link out)

No server endpoint. The settings page renders a static link to the canonical iCloud shortcut URL (set at deploy time via the SHORTCUT_ICLOUD_URL env var, e.g. https://www.icloud.com/shortcuts/abc123...). The shortcut is authored once in the Apple Shortcuts app, with the API base URL hardcoded and an Ask for Input action that prompts for the token on first run, storing it in a persistent shortcut variable named FeedMeToken. A second tile inside the shortcut, "Reset Token," clears that variable so the user can paste a rotated token without rebuilding the shortcut.

POST /api/ingest bearer

Called by the iOS Shortcut. Auth: Authorization: Bearer <api_token>.

// Request
{ "url": "https://example.com/article" }

// 200 OK — new episode queued
{ "status": "pending", "deduped": false }

// 200 OK — already in this user's feed
{ "status": "ready",   "deduped": true }

// 400 — malformed URL
{ "error": "invalid_url" }

// 401 — missing or bad token
{ "error": "unauthorized" }

Response time target: < 200ms. Heavy work runs in the worker loop.

GET /feed/:token.xml public

No auth header; the token in the URL is the auth. Returns valid podcast RSS 2.0 with the iTunes namespace. Includes only episodes with status='ready', ordered newest first. Each <guid> is the episode's audio_token. Cache-Control: max-age=60.

R2 audio URLs public

Audio is served directly from a public R2 bucket via R2's default hostname, e.g. https://pub-XXXXX.r2.dev/audio/{user_id}/{audio_token}.mp3. Anyone with the URL can stream the file — the standard podcast security model. Unguessable audio_token keys keep the bucket effectively private to feed subscribers. A custom domain is backlog.

8. Auth & security

  • Owner account: on first boot the app reads OWNER_EMAIL and OWNER_PASSWORD env vars and seeds the single users row, bcrypt-hashing the password. Subsequent restarts skip the seed step. To rotate the password, change the env var and restart.
  • Browser session: after a successful login the server inserts a sessions row and sets an HttpOnly; Secure; SameSite=Lax cookie. 30-day expiry, sliding on each authenticated request. Logout deletes the row.
  • API token (for the Shortcut): 32 random bytes, base64url. Stored as sha256 hash; plaintext appears in the rendered .shortcut file only. Rotating it from the settings page generates a new value and invalidates the previously-installed shortcut.
  • Feed token: 32 random bytes, base64url. Stored plaintext (it's the credential itself, so hashing would block feed lookups). Capability URL — anyone with it reads your feed. Rotation supported from settings.
  • Audio tokens: 16 random bytes per episode, base64url. R2 bucket has public read on audio/ with listing disabled, so enumeration is infeasible.
  • CSRF: the SameSite=Lax cookie covers the common forgery vectors. A proper CSRF token on POST /settings/* forms is ~5 extra lines and lands alongside the v2.0 multi-user work; for the single-user MVP, the residual risk is negligible (no untrusted users to exploit).
  • Open signup is disabled: v1 supports exactly one user, seeded from env vars. New signups are deferred until v2 (multi-user with magic-link onboarding).
  • No SSRF guardrail or rate limiter in v1. Single user with a static API token; if it leaks, rotate it. Both return for the public release.

9. Error handling

FailureBehavior
Network/HTTP error fetching URLRetry the whole pipeline up to 3 times (via episodes.attempts); then fail with the HTTP status.
Readability returns empty / paywalled bodyInline Wayback fallback within step 1 (§5).
Wayback has no snapshotFail episode: "Couldn't extract article (paywalled and not in Wayback)."
Article over 20k wordsFail episode: "Article too long (over 20k words)."
OpenAI TTS error (rate limit, transient)Retry the whole pipeline up to 3 times with backoff; then fail episode.
R2 upload errorRetry the whole pipeline up to 3 times with backoff; then fail episode.
Worker process crash mid-stepOn startup, any episodes stuck in processing older than 5 min is reset to pending and re-attempted (counted as one attempt).

Failed episodes can be inspected via npm run list-failed (CLI) which prints recent failures with their error_message. The Shortcut response from /api/ingest only reflects acceptance, not eventual outcome — surfacing async failures back to the Shortcut as iOS notifications is a v1.1 enhancement.

10. Deployment

  • Fly.io: one machine, shared-cpu-1x, 512 MB RAM (256 MB is too tight — jsdom + Readability plus buffering N MP3 chunks can spike past it), with a 1 GB volume mounted at /data for SQLite. fly deploy from a standard Node Dockerfile.
  • Domain: Fly's default *.fly.dev hostname is fine for v1 (it's HTTPS by default; the iOS Shortcut and podcast apps don't care about the hostname). A custom domain is backlog.
  • Cloudflare R2: one bucket, public read on audio/ prefix, listing disabled, served from R2's default pub-XXX.r2.dev hostname.
  • Env vars: OPENAI_API_KEY, R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY, R2_BUCKET, R2_PUBLIC_BASE_URL, OWNER_EMAIL, OWNER_PASSWORD, SESSION_SECRET (used to sign session cookies), APP_BASE_URL (the public origin, e.g. https://feed-me-noah.fly.dev), SHORTCUT_ICLOUD_URL (the canonical iCloud share URL for the Feed Me shortcut).
  • Schema: a single schema.sql applied with CREATE TABLE IF NOT EXISTS on startup. A real migration system arrives the first time we actually need to alter a table.
  • Backups: flyctl ssh sftp get the SQLite file occasionally if you care. Fly volumes are reliable enough for a personal tool; no Litestream in v1.
  • Logs: stdout to Fly's log stream; structured JSON via pino.

12. Testing

  • Unit tests: URL normalization, paywall heuristic, Readability output shape, RSS XML rendering, paragraph chunking.
  • Integration tests: end-to-end POST /ingest → DB row → mocked TTS → in-memory R2 stub → feed XML contains episode. Runs against an ephemeral SQLite file.
  • Fixture corpus: a small set of saved HTML pages (paywalled, ad-heavy, simple blog, long-form, non-English) to regression-test extraction.
  • Manual smoke test: after deploy, send 3 real URLs via the Shortcut and confirm episodes appear in a podcast app within 90 seconds.

13. Out of scope & backlog

Explicitly out of scope for v1

  • Spotify support. Spotify's consumer app cannot subscribe to custom RSS URLs and its "private podcast" tooling is enterprise-only. Listeners use Apple Podcasts, Overcast, Pocket Casts, etc.
  • Multi-user signup. v1 supports exactly one owner account, seeded from env vars. Magic-link multi-user lands in v2.0.
  • Custom domain (Fly's default *.fly.dev hostname is used).
  • PDF / file uploads.
  • Raw-text input ("paste this text") Shortcut variant.
  • Per-episode voice override.
  • LLM cleanup or summarization.
  • Multi-part episode splitting (long articles render as one long MP3 via chunked TTS, but stay a single feed entry).
  • iOS notifications on async failure.
  • Episode artwork from og:image.
  • Streaming TTS / progressive playback.
  • Search, transcripts, export.
  • SSRF allowlist, rate limiter, migrations system, Litestream backup — all valid; all deferred until the public release.

Backlog (rough order)

  1. v1.1 Async failure notifications back to the Shortcut (iOS push or email).
  2. v1.2 "Paste text" Shortcut variant for paywalled content not in Wayback.
  3. v1.3 Episode artwork from og:image; custom domain.
  4. v2.0 Multi-user signup with magic-link auth (Resend), public landing page, SSRF allowlist, per-user rate limiter, real migrations system.
  5. v2.x PDF input. Per-episode voice. ElevenLabs as a premium voice tier. Litestream backups. Spotify-compatible feed for users who claim their show via Spotify for Podcasters.
