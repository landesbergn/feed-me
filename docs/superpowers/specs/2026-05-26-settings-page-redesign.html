Settings Page Redesign

Feed Me · 2026-05-26 · spec

The settings page (templates/settings.html) was built fast in v1.0 and never rethought after the friend-onboarding flow landed. It mixes setup, reference info, and settings into a flat 3-step list. This spec restructures it into clear phases so a friend who's never seen Feed Me before can self-serve end-to-end without confusion.

1 · Why

Today's settings page has three numbered "Step" sections that aren't actually a sequence: Step 1 is an action (Install Shortcut), Step 2 mixes an action with a feed URL display, Step 3 is purely reference info (the ingest URL with a manual copy button). The voice picker, recent episodes list, and rotate URL are jammed in below with no hierarchy. Friends opening this page can't tell what to do, in what order, or what they can ignore.

Missing entirely: any guidance on how to actually use the Shortcut after install ("Share an article from Safari → tap Feed Me"). New friends have to figure out the share-sheet flow from cold.

2 · What we're building

A redesigned templates/settings.html that organizes content into three clear phases:

  1. Set up · do this once — install the Shortcut, subscribe in a podcast app
  2. Share an article · do this anytime — three numbered sub-steps for the Safari share flow, with the actual iOS share-sheet icon inline
  3. Recent episodes — table view: article, when shared, status chip (Ready / Pending / Failed)

All settings (voice picker, ingest URL, rotate URL) move into a single collapsible Settings section at the bottom, collapsed by default. Apple Podcasts subscribe and Copy feed URL buttons are paired side-by-side in the same setup step.

This requires a small backend change: episodes need a "pending" state so friends can see that a just-shared article is being worked on (rather than wondering if it was even received). Today's storage writes a record only on success or failure; we need to write a record at ingest start too.

5 · Implementation notes

Files modified

  • templates/settings.html — full rewrite
  • storage.py — new function write_pending_episode; update list_episodes to expose a normalized status field ("ready" | "pending" | "failed")
  • ingest.py — process() writes a pending stub before fetch, then overwrites with the real record on success/failure
  • app.py — the settings route already passes episodes to the template; just augment its render context with a now_ts for the "When" relative-time helper
  • tests/test_storage.py — tests for write_pending_episode and the status field
  • tests/test_ingest.py — assert process() writes a pending record at start and converts it to ready/failed at end
  • tests/test_app.py — update test_settings_renders_for_known_user assertions for the new phase headers and table

Pending state mechanics

Today, ingest.process() writes one record at the end — either via write_episode (success) or write_failed_episode (failure). The new flow:

  1. At start of process(), call write_pending_episode(data_dir, secret, url=url) → slug. This writes <slug>.json with {"title": None, "url": url, "ts": now, "pending": true} and no .mp3.
  2. On success, overwrite <slug>.json with the real title and remove the "pending" flag (or rewrite without it), and write <slug>.mp3.
  3. On failure, overwrite <slug>.json with the error message, remove "pending", leave no .mp3.

list_episodes derives status from the record's fields: "failed" if error is set; "pending" if pending is true; "ready" otherwise (must have audio).

The new write_episode / write_failed_episode signatures gain a slug parameter so the pending record can be promoted in place. Existing call sites in tests need updating.

Relative time display

Render in the Python route, not in JS — the page is server-rendered, no live updates needed. Buckets:

  • < 60 s → "just now"
  • < 60 min → "N min ago"
  • < 24 hr → "N h ago"
  • < 7 d → "N d ago"
  • otherwise → "YYYY-MM-DD"

Implemented as a small helper in app.py (no new module needed) and called per episode at render time. Tabular-nums applied via CSS so columns align.

Inline iOS Share SVG

Defined once in the template head as an <svg><symbol id="ios-share">…, referenced inline via <svg><use href="#ios-share"/></svg>. Sized at 1em with vertical-align: -0.15em so it sits on the baseline next to the surrounding text. Stroked in iOS system blue #007AFF.

Timeline hairline

Same idiom as the landing page: .step-row:not(:last-child)::before renders a 1.5px vertical line at #eaeaea from just below one circle to the top of the next, behind the circle (z-index: 1 on the circle, white background fills). The line is per-phase — both Setup steps connect, both Share steps connect. The hairline does not cross the phase header boundary.

Collapsible Settings

Native <details> / <summary> — no JavaScript needed. Summary styled as a small uppercase label with a chevron that rotates on open. Voice picker, ingest URL display + copy button, and rotate URL button all live inside.

6 · Testing

Storage tests (new)

  • test_write_pending_episode_writes_json_only: creates user, calls write_pending_episode, asserts JSON has pending: True and no MP3 exists.
  • test_list_episodes_status_field: write one pending, one ready, one failed; assert status field equals "pending" | "ready" | "failed" respectively.
  • test_write_episode_promotes_pending: write_pending → write_episode with the same slug → final JSON has no pending flag, has title, MP3 exists.

Ingest tests (updated)

  • test_process_writes_pending_then_ready: monkeypatch with a fake-http that blocks until released; assert that at the mid-point of process() a pending record exists; release; assert the record promoted to ready.
  • Existing failure-path test asserts the promoted record has error set and no pending.

App tests (updated)

  • test_settings_renders_for_known_user: update assertions — "Install Shortcut", "Add to Apple Podcasts", "Copy feed URL", "Share an article", "Tap" in the share step.
  • test_settings_lists_recent_episodes: update to assert table column headers ("Article", "When", "Status") appear, plus the existing title assertion.
  • New: test_settings_pending_episode_renders_with_pending_status — write a pending episode via storage, render settings, assert "Pending" chip appears.

7 · Out of scope

  • Live status updates. Page is server-rendered; pending → ready transition only visible after a manual refresh.
  • Episode playback on the settings page. Listening happens in the podcast app, not here.
  • Per-episode delete / retry. A failed episode stays in the table indefinitely as a signal; no UI to remove or retry.
  • Pagination. Existing 30-record cap is fine.
  • Landing page changes. Out of scope; that was v1.1.

8 · Known follow-ups future

  • Live status updates via polling or SSE. If pending → ready transitions take more than a refresh to notice, a small JS poll could update the chips in place. Not worth doing until friends complain.
  • Auto-bookmark prompt. Friends who skip bookmarking lose their feed forever. A more aggressive interrupt (full-screen confirmation between /create and the settings page) was raised in v1.1 and is still open.
  • Per-episode retry on failure. Single tap to re-fetch a failed URL. Would be useful for transient errors (timeouts, 429s) but not for permanent ones (paywalls). Out of v1.3 to keep scope tight.

9 · Acceptance criteria

  • templates/settings.html rewritten with the three-phase structure above
  • storage.py exports write_pending_episode; list_episodes returns records with a status field
  • ingest.process() writes a pending stub before fetch and promotes it on success or failure
  • All existing tests still pass; new tests for pending state pass
  • Deployed to https://feed-me.xyz; visiting /u/<secret> shows the new layout
  • On iPhone Safari portrait (iPhone 14-class), the page is readable end-to-end without horizontal scroll
  • Sharing an article via the Shortcut results in a row appearing on the settings page with Pending status within the first refresh after sharing, then Ready after ~60 s
