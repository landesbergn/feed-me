TTS Chunking + Length Cap

Feed Me · 2026-05-27 · spec

Today every article body is silently truncated to TTS_CHAR_LIMIT = 4000 before going to OpenAI TTS, because that's the model's per-call input cap. A typical article runs 6-15k chars, so most audio cuts off mid-sentence around the four-minute mark. This fixes that with sentence-aware chunking, plus a 100k char hard ceiling (~50 min of audio, ~$1.50 of TTS) above which we fail the episode rather than risk a surprise bill.

1 · Why

synthesize in ingest.py does: 

response = openai_client.audio.speech.create(
    model=TTS_MODEL,
    voice=voice,
    input=text[:TTS_CHAR_LIMIT],  # ← silently truncated to 4000 chars
)

The 4000-char limit is OpenAI's, not ours — tts-1 rejects longer input. The fix is to call TTS multiple times and concatenate the MP3 bytes. MP3 frames are self-contained, so naive byte concatenation produces a valid playable file (verified by the user with their Notion article observation; modern podcast apps handle this fine).

2 · What we're building

  1. A new helper chunk_text(body, max_chars) → list[str] that splits long text into chunks ≤ max_chars at sentence boundaries when possible, falling back to word boundaries, then hard cuts only if a single word/sentence is longer than max_chars.
  2. Replace synthesize's single TTS call with a loop over chunks; concatenate the response bytes; return the combined MP3.
  3. In process(), before chunking, check len(body) > 100_000. If so, raise an explicit exception with a clear message; write_failed_episode records it.

3 · Chunking strategy

For each chunk we want it to be ≤ 4000 chars (the TTS-1 hard cap). Three priorities:

  1. Split at the last sentence boundary (. + space, ! + space, ? + space) before the cap.
  2. If no sentence boundary in the window, split at the last word boundary (space) before the cap.
  3. If no spaces (unlikely — a 4000-char run with no spaces is extraordinary), hard-cut at the cap.

Algorithm

def chunk_text(body: str, max_chars: int) -> list[str]:
    """Split body into chunks <= max_chars, preferring sentence boundaries."""
    chunks = []
    pos = 0
    while pos < len(body):
        end = pos + max_chars
        if end >= len(body):
            chunks.append(body[pos:].strip())
            break
        window = body[pos:end]
        # 1. Try sentence boundary
        split_at = max(
            window.rfind(". "),
            window.rfind("! "),
            window.rfind("? "),
        )
        if split_at == -1 or split_at < max_chars * 0.5:
            # 2. Fall back to word boundary
            split_at = window.rfind(" ")
        if split_at == -1:
            # 3. Hard cut
            split_at = max_chars
        else:
            split_at += 1  # include the punctuation/space in chunk
        chunks.append(body[pos:pos + split_at].strip())
        pos += split_at
    return [c for c in chunks if c]

The 50%-of-cap minimum (split_at < max_chars * 0.5) avoids producing tiny chunks when sentence boundaries happen to land near the start of the window.

MP3 concatenation

OpenAI returns raw MP3 bytes per chunk. Naive concatenation produces a valid playable MP3 stream — each chunk is independent ID3-less frames. Tested in practice; podcast apps handle it.

Latency note

Each TTS-1 call takes ~3-5 seconds. A 4-chunk article takes ~15-20s. The user's experience: Pending row appears within ~3s (unchanged — fetch_title runs before chunking), then Ready chip appears 15-30s later instead of the current 30-60s for truncated single-call episodes. Net feeling: slower per share, but the episode is complete.

4 · 100k cap behavior

Before invoking chunk_text, process() checks: 

MAX_BODY_CHARS = 100_000  # ~50 minutes of TTS audio, ~$1.50 max cost

if len(body) > MAX_BODY_CHARS:
    raise ValueError(
        f"Article too long: {len(body):,} chars (limit: {MAX_BODY_CHARS:,}). "
        f"Try sharing a shorter article, or the original URL works in browser."
    )

The exception propagates to the existing except Exception as e block in process(), which calls write_failed_episode with str(e)[:200]. The failed row appears in the settings table with the error message visible to the user.

UX effect on the failed row

Today a failed row reads "(couldn't extract article)" in the title slot and shows the error in the source URL area. With this change, the same UI applies — the error string starts with "Article too long: N,NNN chars..." which is clearly self-explanatory.

5 · Implementation notes

Modified files

  • ingest.py — new chunk_text(body, max_chars) → list[str] helper, new MAX_BODY_CHARS = 100_000 constant, updated synthesize to chunk and concatenate, updated process() to check the body cap before synthesize.
  • tests/test_ingest.py — tests for chunk_text (short body returns one chunk, long body splits at sentence boundary, very long body splits multiple times, no-sentence body falls back to word boundary); test that synthesize calls TTS multiple times and concatenates bytes; test that process raises and writes a failed episode when body exceeds the cap.

synthesize signature stays the same

Externally, synthesize(text, voice) → bytes still returns combined MP3 bytes. Internally it now loops: 

def synthesize(text: str, voice: str) -> bytes:
    chunks = chunk_text(text, TTS_CHAR_LIMIT)
    parts = []
    for chunk in chunks:
        response = openai_client.audio.speech.create(
            model=TTS_MODEL,
            voice=voice,
            input=chunk,
        )
        parts.append(response.content)
    return b"".join(parts)

The text[:TTS_CHAR_LIMIT] truncation is gone — replaced by proper chunking.

FakeOpenAI test fixture

The existing FakeOpenAI fixture in tests/conftest.py records each TTS call's kwargs in fake_openai.calls. With chunking, multiple calls are made — tests can assert len(fake_openai.calls) equals the expected chunk count, and concatenate fake_openai.audio_bytes N times to match the returned bytes.

No changes needed

The existing storage / RSS / app / template tests are unaffected — chunking is purely internal to synthesize.

7 · Out of scope

  • Configurable per-user limits. 100k applies to everyone.
  • Switching to a longer-context TTS model. Even tts-1-hd has the same 4096 cap. OpenAI's newer gpt-4o-mini-tts may have different limits; not v1.7.
  • Parallel chunked TTS calls. Could halve latency by parallelizing via asyncio.gather or a thread pool, but adds complexity. v1.7 stays sequential.
  • Progress indication during multi-chunk processing. Pending row just shows "Pending" the whole time. No "chunk 2 of 5" updates.
  • MP3 stitching with re-encoding. Naive concat works; we don't need ffmpeg.

8 · Known follow-ups future

  • Parallel TTS calls. If you regularly share long-form essays, halving latency by running chunks concurrently is worth it. Adds ~30 LOC.
  • Switch to gpt-4o-mini-tts. Better quality, possibly different char limits. Worth evaluating once it's stable.
  • Stream the audio bytes to the volume as chunks arrive. Today we buffer everything in memory before writing the MP3. For 50-min articles that's 50-100MB in RAM. Streaming would be more memory-friendly. Not urgent for hobby use.

9 · Acceptance criteria

  • A 6-15k char article (most real articles) is fully narrated end-to-end — no truncation, no cutoff at the 4-minute mark.
  • A 100k+ char article produces a Failed episode with the error message "Article too long: NNN,NNN chars (limit: 100,000)…" visible in the settings table.
  • The Notion article that triggered this report, when re-shared, plays through to the end.
  • All existing tests pass; new tests pass.
  • No new dependencies. No changes to storage, RSS, or template layer.

Brainstormed via terminal Q&A on 2026-05-27. Chunking at sentence boundaries chosen for narration quality. 100k cap with hard error chosen over silent truncation for cost-control transparency.
