Pending Progress Indicator

Feed Me · 2026-05-29 · spec

After sharing an article, the row sits at "Pending" for 60-90 seconds with no feedback. Friends don't know if it's stuck or making progress. This spec adds a smooth percent indicator computed client-side from elapsed time and the article's chunk count, so the Pending chip becomes "Pending · 42%" ticking up smoothly until the row flips to Ready.

1 · Why

After v1.8 (parallel TTS), typical articles ingest in ~60-90s. That's fast in absolute terms but feels long when you're staring at "Pending" with no movement. The user asked for a progress indicator that ticks smoothly so the page doesn't feel dead.

Why not show real "X of N chunks done"? Because TTS calls run fully parallel — chunk completions burst (0/13 for 30s, then 7/13 in two seconds, then 13/13). That's worse UX than a smooth interpolation: the eye sees zero progress for half the wait, then a jump. Better to show a smooth time-based curve.

2 · What we're building

  1. Backend: after chunk_text runs in ingest.process(), update the pending record with total_chunks via a new storage.update_pending_episode() helper.
  2. Backend: list_episodes exposes total_chunks on each episode dict (defaults to None when not set).
  3. Frontend: in templates/_episodes_section.html, each Pending row carries data-ts (start timestamp) and data-chunks (total chunk count) attributes on a new <span class="pending-progress">.
  4. Frontend: a small JS ticker (1Hz) in templates/settings.html recomputes the percent for each pending row and updates the text in place.

3 · Percent calculation

Client-side, recomputed every second:

const SECONDS_PER_CHUNK = 5;
const MIN_EXPECTED_SECONDS = 30;
const MAX_DISPLAY_PERCENT = 95;

function computePercent(startTs, totalChunks) {
  const nowTs = Math.floor(Date.now() / 1000);
  const elapsed = nowTs - startTs;
  const expected = Math.max(MIN_EXPECTED_SECONDS, (totalChunks || 1) * SECONDS_PER_CHUNK);
  const raw = (elapsed / expected) * 100;
  return Math.min(MAX_DISPLAY_PERCENT, Math.max(0, Math.round(raw)));
}

The 95% cap exists so we never claim "100% done" while still processing. When the row actually flips to Ready via the 3s polling, the status chip changes from "Pending · 92%" to "Ready" — visually distinct enough that the cap isn't jarring.

The 5s-per-chunk constant is calibrated to v1.8's observed wall time for the Notion article (~67s for 13 chunks ≈ 5.2s/chunk). Tunable as a module-level constant.

4 · Implementation notes

New storage helper

def update_pending_episode(
    data_dir: Path, secret: str, slug: str, *,
    total_chunks: int | None = None,
) -> None:
    """Update fields on an existing pending episode record.

    Reads the JSON, updates the specified fields, writes back. Existing
    fields preserved. No-op if the record doesn't exist.
    """
    path = data_dir / secret / f"{slug}.json"
    if not path.exists():
        return
    record = json.loads(path.read_text())
    if total_chunks is not None:
        record["total_chunks"] = total_chunks
    path.write_text(json.dumps(record))

process() change in ingest.py

Insert the chunking + write between fetch_article and synthesize:

def process(url: str, secret: str, data_dir: Path, slug: str | None = None) -> None:
    if slug is None:
        slug = storage.write_pending_episode(data_dir, secret, source_url=url)
    try:
        title, body = fetch_article(url)
        if len(body) > MAX_BODY_CHARS:
            raise ValueError(...)
        # NEW: write total_chunks to pending record so JS can compute %
        chunks = chunk_text(body, TTS_CHAR_LIMIT)
        storage.update_pending_episode(
            data_dir, secret, slug, total_chunks=len(chunks),
        )
        settings = storage.get_settings(data_dir, secret)
        audio = synthesize(body, settings["voice"])
        ...

Note: chunk_text runs twice (here AND inside synthesize). That's fine — it's pure-Python string ops on ~50k chars, <10ms. Avoids changing synthesize's public signature.

list_episodes change

Already returns data dict directly from the JSON. The new total_chunks key flows through unchanged. No code change needed — callers (template) can just access ep.total_chunks when present.

Template change in _episodes_section.html

Inside the Pending branch of the status cell:

{% elif ep.status == "pending" %}
  <span class="status-chip pending">Pending</span>
  <span class="pending-progress"
        data-ts="{{ ep.ts }}"
        data-chunks="{{ ep.total_chunks or 0 }}"></span>

The empty <span> is filled by JS with text like "42%". On first render before JS ticks, it's empty (acceptable — fills within 1s).

JS ticker in settings.html

Add a new IIFE inside the existing <script> area at the bottom of settings.html:

<script>
  (function () {
    const SECONDS_PER_CHUNK = 5;
    const MIN_EXPECTED_SECONDS = 30;
    const MAX_DISPLAY_PERCENT = 95;

    function tick() {
      const nowTs = Math.floor(Date.now() / 1000);
      document.querySelectorAll(".pending-progress").forEach(function (el) {
        const startTs = parseInt(el.dataset.ts, 10);
        const totalChunks = parseInt(el.dataset.chunks, 10);
        if (!startTs) return;
        // If total_chunks isn't set yet (fetch_article still running),
        // don't show a percent — the unknown-window estimate would later
        // jump DOWN when the real total_chunks arrives, violating
        // "percent never goes backwards".
        if (!totalChunks || totalChunks < 1) {
          el.textContent = "";
          return;
        }
        const elapsed = nowTs - startTs;
        const expected = Math.max(MIN_EXPECTED_SECONDS, totalChunks * SECONDS_PER_CHUNK);
        const pct = Math.min(MAX_DISPLAY_PERCENT, Math.max(0, Math.round((elapsed / expected) * 100)));
        el.textContent = pct + "%";
      });
    }
    tick();
    setInterval(tick, 1000);
  })();
</script>

Runs every second regardless of tab visibility (cheap; no fetch). The existing 3s episodes-partial polling replaces #episodes-section innerHTML when new data arrives; the next tick() after the swap picks up the fresh data-ts/data-chunks attributes from the new DOM.

Why we hide percent until total_chunks is real: the row exists from t=0 (pending stub written immediately) but total_chunks only lands after fetch_article completes (1-10s later, depending on the URL). If we showed a percent based on a fallback expected-time during that window, the percent could be 33% at t=10s on the fallback (10/30) and then drop to 11/65 = 17% once the real total_chunks=13 arrives. That violates the "never backwards" acceptance criterion. Showing nothing until real data is the simplest fix.

5 · Testing

Storage tests (new)

  • test_update_pending_episode_sets_total_chunks — write pending, call update_pending_episode with total_chunks=13, list_episodes returns the record with total_chunks == 13 and all other fields (title, url, ts, pending) preserved.
  • test_update_pending_episode_noop_when_missing — call on a non-existent slug, returns without raising; no file created.

Ingest tests (new)

  • test_process_writes_total_chunks_before_synthesize — mirrors v1.7's test_process_writes_pending_then_ready pattern. Monkey-patch ingest.synthesize to observe storage state at call time; assert the pending record visible at that moment has total_chunks >= 1. (Cannot assert on the post-completion record: write_episode writes a fresh dict without total_chunks, by design — the field is only meaningful while pending.)

App tests (new)

  • test_settings_pending_row_has_data_attributes — write a pending episode with total_chunks=5 via update_pending_episode; render settings; assert the response contains both data-ts=" and data-chunks="5".

No JS test

The percent calculation is ~5 lines of pure math. Verified by eye + the % values in the table above. Not worth a JS test harness.

6 · Out of scope

  • chunks_done tracking. Parallel completion bursts make this misleading; smooth time-based progress is better UX.
  • Separate ETA number. Percent + the existing "When" column tell the story together.
  • Real-time WebSocket updates. The existing 3s polling is fast enough for status transitions.
  • Calibrating SECONDS_PER_CHUNK from real data. Hardcoded 5s for v2.0; could tune later based on logs.
  • Pause/cancel button. No way to stop an in-flight ingest from the UI.

7 · Known follow-ups future

  • Adaptive timing. Track real ingest durations server-side, use a rolling average as the per-chunk estimate instead of a hardcoded constant.
  • Visible progress bar. A small horizontal bar instead of (or in addition to) the percent text. More work, marginal UX gain.
  • Stuck-pending detection. If percent has been at 95% for >5min, show "Taking longer than usual..." or auto-mark failed.

8 · Acceptance criteria

  • After sharing a long article, the Pending row shows a percent that ticks up every second.
  • Percent never goes backwards.
  • Percent caps at 95% until the actual completion happens (then row flips to Ready).
  • For the typical 13-chunk Notion article, the percent reads ~46% at 30s elapsed, ~92% at 60s.
  • Tab switching doesn't break anything: tick runs in background; on tab refocus the next swap from polling refreshes the data attributes.
  • All existing tests pass; 3 new tests pass.

Brainstormed via terminal Q&A on 2026-05-29. Time-based smooth percent chosen over real chunks-done count to avoid burstiness UX. 5s-per-chunk calibration based on v1.8's observed 67s wall time for 13 chunks. No new dependencies.
