Episode Metadata + Apple Podcasts Compatibility

Feed Me · 2026-05-27 · spec

Three coupled fixes for the post-share experience. (1) the Pending row currently reads "(couldn't extract article)" — misleading since the article hasn't actually failed; (2) RSS items have no descriptions so the source URL and a snippet don't show up in podcast apps; (3) Apple Podcasts silently refuses to subscribe to the feed (Overcast accepts it).

1 · Why

v1.5 delivered live updates and the welcome episode — friends can now subscribe to an empty feed and watch shares appear. But three rough edges undercut the experience:

  • The Pending row reads "(couldn't extract article)" because the template uses that string as the fallback whenever title is None. None means two different things: "ingest hasn't happened yet" (pending) vs. "extraction actually failed". They deserve different fallbacks.
  • RSS items only carry title/link/guid/pubDate/enclosure. No description, no summary, no excerpt. In Apple Podcasts the episode preview shows blank — the source URL and article context are invisible.
  • Apple Podcasts refuses to subscribe (verified by the user; Overcast works). The feed is valid RSS 2.0 but missing a few iTunes/atom elements Apple requires and has one definitely-wrong attribute (length="0" on every enclosure).

2 · What we're building

  1. Quick title fetch at /ingest time. Before spawning the worker thread, do a fast HTTP GET on the URL, parse just the HTML <title>, store as the pending record's title. Costs ~1-2s of added latency on the ingest endpoint; in exchange the Pending row shows the real title from ~1s in.
  2. Per-episode descriptions. Add a description field to the episode JSON. For shared articles, store the first ~200 chars of the extracted plain-text body. For the welcome, a hand-written one-liner. Render in <description> and <itunes:summary> at the item level.
  3. Apple Podcasts fixes. Compute and emit real length bytes on each <enclosure>. Add <atom:link rel="self"> and <itunes:type>episodic</itunes:type> to the channel. Change the podcasts:// deep link in settings.html to podcast:// (singular — Apple's documented scheme).

3 · Quick title fetch on /ingest

Behavior

Today the /ingest route validates the URL, calls spawn_ingest(), returns {"ok": true}. The pending record written by the worker thread has title: None.

The new flow:

  1. /ingest validates the URL.
  2. Synchronously calls a new helper ingest.fetch_title(url) → str | None that does an HTTP GET (with a tight 5s timeout) and extracts the <title> tag. Returns the title text, or None on any failure (timeout, no title, parse error).
  3. Writes the pending record with this title via a new signature storage.write_pending_episode(data_dir, secret, *, source_url, title=None).
  4. Spawns the worker thread as before, which later promotes the record (and over-writes the title with the Readability-extracted one, which may be the same or better).

Failure handling

If fetch_title returns None — network error, no title tag, anything — the pending record gets title: None and the template falls back to showing the hostname (see §3 template change below). The worker still runs normally and may succeed with a Readability-extracted title.

Template change

The episode-section partial currently has:

{{ ep.title or "(couldn't extract article)" }}

Change to:

{% if ep.title %}{{ ep.title }}{% elif ep.status == "pending" %}Loading from {{ ep.url | hostname }}…{% else %}(couldn't extract article){% endif %}

Where | hostname is a small new Jinja filter that strips scheme and path from a URL (returns colossus.com from https://colossus.com/article/inside-notion/).

4 · Per-episode descriptions

Storage shape

Episode JSON gains a description field, optional. When set, the RSS feed renders it in <description> and <itunes:summary>.

Content rules

Episode typeDescription content
Shared article (ready)First ~200 chars of the Readability-extracted plain-text body, then "…" if truncated. Followed by a newline and the source URL.
Shared article (pending)None (description not yet available; rendered as just the source URL in the feed).
Shared article (failed)The error string + the source URL.
Welcome"Share an article from your phone — it'll show up here a minute later." (hand-written).

Storage signatures

write_episode, write_pending_episode, and write_failed_episode all accept a new optional description: str | None = None keyword. When provided, it's written into the episode JSON.

seed_welcome_episode always writes the hard-coded welcome description above.

RSS template additions

Inside <item>, after <pubDate>:

<description>{{ ep.description or ep.url | e }}</description>
<itunes:summary>{{ ep.description or ep.url | e }}</itunes:summary>

Fallback to the source URL if no description is set (pending case, mostly).

5 · Apple Podcasts compatibility

Enclosure length

Today every enclosure has length="0". Apple Podcasts often rejects this. Compute the real byte size from the MP3 file when rendering the feed.

Implementation: in list_episodes, look up (user_dir / f"{slug}.mp3").stat().st_size when the file exists, attach as audio_bytes on the dict. Template renders length="{{ ep.audio_bytes or 0 }}" (defaults to 0 for items with no audio, which are filtered out anyway since they're not ready).

New channel elements

Add to <channel>:

<atom:link href="{{ feed_url }}" rel="self" type="application/rss+xml"/>
<itunes:type>episodic</itunes:type>

Also add the xmlns:atom="http://www.w3.org/2005/Atom" namespace declaration to the <rss> root.

Deep link scheme

Change in templates/settings.html: 

<!-- before -->
<a href="podcasts://{{ feed_host_and_path }}">Add to Apple Podcasts</a>

<!-- after -->
<a href="podcast://{{ feed_host_and_path }}">Add to Apple Podcasts</a>

podcast:// (singular) is Apple's documented URL scheme for subscribing to a custom RSS feed. podcasts:// (plural) used to work but is no longer the canonical form.

Note on Apple's feed cache

Apple aggressively caches feeds. After deploy, an already-failed subscription attempt may continue to fail because Apple keeps serving its cached bad version. To force a fresh fetch: either rotate the user's URL (gives Apple a feed URL it's never seen), or unfollow + wait ~5 minutes + retry. This is an Apple limitation, not something we can fix in code.

Hostname filter

Small Jinja filter registered on the FastAPI Jinja2Templates instance. Takes a URL string, returns the hostname (no scheme, no port, no path). E.g. https://colossus.com/article/foo → colossus.com. Implemented via urllib.parse.urlparse.

fetch_title implementation sketch

def fetch_title(url: str, *, timeout: float = 5.0) -> str | None:
    """Quick HTTP GET to extract just the <title> tag. Returns None on any failure."""
    try:
        resp = http_client.get(url, timeout=timeout)
        resp.raise_for_status()
    except Exception:
        return None
    # Parse just the title tag — don't run full Readability here, that's the worker's job
    try:
        doc = lxml_html.fromstring(resp.text)
        title_el = doc.find(".//title")
        if title_el is not None and title_el.text:
            return title_el.text.strip() or None
    except Exception:
        return None
    return None

Worker thread interaction with fetched title

The worker calls fetch_article as before, getting the Readability title. When it calls write_episode(slug=slug, title=readability_title, ...), the pending record's title gets overwritten. If the Readability title is the same or better than the <title> tag, this is fine. If different — Readability wins, which is usually correct (its title-cleaning logic strips site-name suffixes).

Description from Readability body

fetch_article already returns (title, body). process truncates the body to 200 chars (preserving word boundaries) plus an ellipsis, and passes as the description to write_episode.

8 · Out of scope

  • Per-episode <itunes:image>. Channel image inherits to all episodes.
  • Per-episode <itunes:duration>. Would need to parse MP3 duration via mutagen or similar; previously called out as a future item.
  • <itunes:owner> / <itunes:category>. Required only for Apple Podcasts Connect submission to the public directory. Not needed for arbitrary RSS subscription.
  • Forcing Apple's cache invalidation. No client-side fix; user must rotate URL or wait.
  • AI-summarized descriptions. First-200-chars-of-body is fine; an LLM summary would be a more interesting future feature, not v1.6.

9 · Known follow-ups future

  • Episode duration tag. Carried over from v1.4 and v1.5. Becomes more attractive now that we're touching the enclosure tag (we'd parse the MP3 with mutagen once at write time and store both audio_bytes and duration_seconds in the episode JSON).
  • LLM-generated episode summary. First 200 chars of the body is OK but not great for long-form pieces. An OpenAI completion call after TTS could produce a real 2-3 sentence summary. Adds a few cents per episode and a few seconds of latency.
  • Apple Podcasts directory submission. If Feed Me grows beyond a small friend group, you might want each feed visible in Apple's search. Requires <itunes:owner> + <itunes:category> + a separate submission step through Apple Podcasts Connect. Not v1.6.

10 · Acceptance criteria

  • Sharing an article via the Shortcut causes the Pending row to appear within ~3s with the article's real title, not "(couldn't extract article)".
  • Each RSS item has a non-empty <description> containing either a body excerpt + URL (ready) or the source URL (pending) or the error + URL (failed).
  • Each <enclosure> has a real byte-count length attribute.
  • The feed channel includes <atom:link rel="self"> and <itunes:type>episodic</itunes:type>.
  • The "Add to Apple Podcasts" button links to podcast://... (singular).
  • After deploy + rotating the user's URL, subscribing to the feed in Apple Podcasts succeeds (Follow button enables, episodes appear).
  • All existing tests pass; new tests pass.

Brainstormed via terminal Q&A on 2026-05-27. Quick title fetch chosen over template-only fallback. Per-item descriptions use first 200 chars of body. Apple fix is multi-pronged because no single missing element is provably the cause — three additions + one scheme change cover the most likely culprits.
