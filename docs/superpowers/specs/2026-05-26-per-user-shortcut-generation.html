Per-User Shortcut Generation

Feed Me · 2026-05-26 · spec

Closes the "Install Shortcut goes nowhere" gap. After this work, when a friend taps "Install Shortcut" on their settings page, iOS opens an install card for a Shortcut that already has their personal ingest URL baked in — no paste, no manual edit.

1 · Why

v1.1 ships a polished landing page that ends in a clear CTA. After the friend creates a feed, the settings page shows an Install Shortcut button — but today it points at the placeholder URL https://www.icloud.com/shortcuts/PLACEHOLDER because we never wired SHORTCUT_ICLOUD_URL.

The original design called for one canonical iCloud-shared Shortcut that every friend installs and then customizes with their own ingest URL. That requires a paste step (using Apple's Import Questions feature). The user decided that even one paste is too much friction: friends should not have to think. Per-user shortcut generation removes the paste at the cost of a one-time "Untrusted Shortcut" warning.

2 · What we're building

A new route GET /u/{secret}/shortcut.shortcut that returns a binary-plist .shortcut file customized for that user. The settings page's "Install Shortcut" button links to this route. When tapped on iPhone Safari, iOS recognizes the content type, opens Shortcuts, shows the install card with a one-time "not from a trusted source" warning, the friend taps "Add Anyway", and the shortcut is installed with their ingest URL pre-baked.

The generated Shortcut should be the simplest possible thing that works:

  1. Accept a URL from the share sheet (Shortcut Input)
  2. Construct <ingest_url>?url=<encoded shared URL>
  3. GET that URL
  4. Show a notification on success (optional, but recommended for feedback)

No options, no settings, no menu prompts. One-purpose Shortcut.

3 · Approach

Generating Apple's .shortcut binary plist from scratch is risky — the format is reverse-engineered and Apple has changed it across iOS versions. Instead, we treat one exported Shortcut as a template:

  1. On iPhone, the user (Noah) exports a working "Feed Me" Shortcut as a .shortcut file (via Shortcuts app → Share → Save to Files). That file is committed to the repo at shortcut_template.shortcut.
  2. At request time, the server reads the template, decodes it with Python's stdlib plistlib, walks the action tree to find the Text action holding the ingest URL, replaces its value with the per-user URL, and re-encodes back to binary plist.
  3. The response is served with Content-Type: application/x-shortcut.

Because the template was authored by iOS itself, every field iOS expects is present and correctly formatted. We only mutate one string. This minimizes our exposure to format drift.

4 · Accepted tradeoff: "Untrusted Shortcut" warning known

Shortcuts not installed via an iCloud-shared URL trigger an iOS card that reads roughly "This shortcut is not from a trusted source." The user must tap an "Add Anyway" / "Add Shortcut" button to proceed. There is no way to suppress this for unsigned per-user shortcuts — only Apple-curated shortcuts in the App Gallery skip the warning, and submission to the Gallery is by Apple's invitation only.

The friend journey, end-to-end:

  1. Visit https://feed-me.xyz/
  2. Tap "Get my feed" → arrive at their settings page
  3. Tap "Install Shortcut" → iOS downloads the per-user .shortcut and opens Shortcuts
  4. "This shortcut is not from a trusted source" warning → tap Add Anyway
  5. Shortcut install card shows actions preview → tap Add Shortcut
  6. Share an article from Safari → tap "Feed Me" in the share sheet → done

Four taps, no paste, no copy. One scary warning.

5 · Implementation notes

New files

  • shortcut_template.shortcut — binary plist exported by user on iPhone. Committed to the repo. Roughly 2-5 KB.
  • shortcut_gen.py — single module with one public function: build_shortcut(template_bytes: bytes, ingest_url: str) → bytes.
  • tests/test_shortcut_gen.py — unit tests for the generator.

Modified files

  • app.py — add a new route GET /u/{secret}/shortcut.shortcut; remove the obsolete SHORTCUT_ICLOUD_URL environment variable plumbing.
  • templates/settings.html — change the "Install Shortcut" button's href from {{ shortcut_url }} to /u/{{ secret }}/shortcut.shortcut.
  • tests/test_app.py — add tests for the new route (200 with correct content-type, 404 for unknown user, response body contains the user's ingest URL).

Generator algorithm

Pseudocode for build_shortcut:

def build_shortcut(template_bytes: bytes, ingest_url: str) -> bytes:
    workflow = plistlib.loads(template_bytes)  # binary → dict

    actions = workflow["WFWorkflowActions"]
    for action in actions:
        if action.get("WFWorkflowActionIdentifier") == "is.workflow.actions.gettext":
            params = action.get("WFWorkflowActionParameters", {})
            text = params.get("WFTextActionText")
            if text and "/u/" in str(text) and "/ingest" in str(text):
                params["WFTextActionText"] = ingest_url
                return plistlib.dumps(workflow, fmt=plistlib.FMT_BINARY)

    raise ValueError("template has no ingest-URL Text action to substitute")

The walk identifies the Text action holding the ingest URL by content match (substring /u/ and /ingest) rather than by position, so the template can be re-exported in the future without breaking the substitution as long as the Text action's identifying pattern is preserved.

Route

SHORTCUT_TEMPLATE = Path(__file__).parent / "shortcut_template.shortcut"


@app.get("/u/{secret}/shortcut.shortcut")
def shortcut_route(secret: str):
    if not storage.user_exists(DATA_DIR, secret):
        raise HTTPException(404)
    ingest_url = f"{APP_BASE_URL}/u/{secret}/ingest"
    template_bytes = SHORTCUT_TEMPLATE.read_bytes()
    body = shortcut_gen.build_shortcut(template_bytes, ingest_url)
    return Response(
        content=body,
        media_type="application/x-shortcut",
        headers={"Content-Disposition": 'attachment; filename="Feed Me.shortcut"'},
    )

The Content-Disposition: attachment header with a friendly filename is what iOS Safari uses to label the install card.

Removing SHORTCUT_ICLOUD_URL

No longer needed. Remove from app.py:

  • The SHORTCUT_ICLOUD_URL = os.environ.get(...) declaration
  • The "shortcut_url": SHORTCUT_ICLOUD_URL entry in the settings template render context

Remove the corresponding {{ shortcut_url }} usage from templates/settings.html. Also delete the Fly secret: fly secrets unset SHORTCUT_ICLOUD_URL.

6 · Testing

Unit tests for shortcut_gen.py

  • Round-trip: given the committed template, calling build_shortcut(template_bytes, "https://example.com/u/abc/ingest") returns bytes that decode as a valid plist, contain the substituted URL, and don't contain the original placeholder URL anywhere.
  • No match raises: given a synthetic plist that has no Text action containing /u/ and /ingest, build_shortcut raises ValueError.
  • Output is binary plist: result starts with the binary plist magic bytes b"bplist00".

Route tests in test_app.py

  • test_shortcut_route_returns_plist: create a user, GET /u/{secret}/shortcut.shortcut, assert 200, assert content-type application/x-shortcut, assert response bytes contain the user's secret somewhere (since the ingest URL substituted in includes the secret).
  • test_shortcut_route_404_for_unknown_user: GET on an unknown secret, assert 404.
  • test_shortcut_filename_in_disposition: assert the Content-Disposition header contains filename="Feed Me.shortcut".

Manual verification

On the user's iPhone, after deploy:

  1. Visit https://feed-me.xyz/u/<current secret>
  2. Tap "Install Shortcut"
  3. Confirm the install card appears with the warning, tap "Add Anyway"
  4. Confirm the installed Shortcut shows the correct ingest URL in its Text action
  5. Share an article from Safari, confirm an episode appears on the settings page within ~60s

Until manual verification passes, the work isn't done — generated shortcuts that "look right" but fail to install or run on a real device aren't useful.

7 · Required manual prerequisite

Before any code can be written, the user (Noah) must produce the template file:

  1. On iPhone, open Shortcuts → tap the working "Feed Me" Shortcut
  2. Tap the Share icon → Save to Files → save as shortcut_template.shortcut
  3. AirDrop or otherwise transfer to the Mac into /Users/noah/Desktop/feed-me/
  4. Verify with file shortcut_template.shortcut — should report "Apple binary property list" or similar
  5. Commit it to the repo before implementation begins

Without the template, the implementer is blocked. The plan should make this prerequisite explicit and verify it as the first task before any other work.

8 · Out of scope

  • App Gallery submission. Apple curates the Gallery; there's no public submission process. Documented as aspirational under follow-ups.
  • Per-user shortcut customization (voice picker, etc.). The generated Shortcut is one-purpose. Voice/other settings stay on the settings page.
  • Shortcut signing. Requires Apple Developer signing infrastructure; out of scope for a self-serve hobbyist tool.
  • Detecting whether the friend bailed at the "Untrusted" warning. Impossible from a web page; the friend either completes install or doesn't, and we don't get a signal either way.

9 · Known follow-ups future

  • App Gallery submission. If Feed Me grows past a small friend group and you want the warning-free install experience, the path is to pitch Apple Shortcuts' curation team. Not a thing we can engineer toward; it's a thing that happens to a product.
  • Improve "Bookmark this page" onboarding (also called out in the v1.1 spec). Friends who forget to bookmark lose their feed forever; the warning the settings page shows today is easy to miss.
  • Auto-update the template when iOS Shortcuts format changes. When a future iOS update changes the binary plist schema, we'll need to re-export the template on iPhone. This may break silently. Consider a startup-time validation step that decodes the template and confirms it has the expected Text action structure, failing loud at boot rather than at request time.

10 · Acceptance criteria

  • shortcut_template.shortcut committed to the repo
  • shortcut_gen.py exports build_shortcut with the documented signature
  • All unit and route tests pass
  • On a real iPhone visiting https://feed-me.xyz/u/<secret>, tapping "Install Shortcut" downloads a .shortcut, the install card appears with the warning, "Add Anyway" → "Add Shortcut" works, and the installed Shortcut's Text action shows the correct ingest URL
  • Sharing an article from Safari through the installed Shortcut results in an episode appearing on the settings page within ~60s
  • The old SHORTCUT_ICLOUD_URL env var and template-render slot are fully removed

Decided via terminal Q&A on 2026-05-26. User accepted the "Untrusted Shortcut" warning as an acceptable tradeoff for zero-paste install. The longer-term path to a warning-free experience is Apple's App Gallery, which is by-invitation only.
