Spec · v1.4

Feed Metadata + Cover Art

Feed Me · 2026-05-26 · spec

Two small but high-impact additions to the RSS feed: a richer channel description and a cover image. Both make every user's feed look like a "real" podcast in Apple Podcasts / Overcast / Pocket Casts library views.

1 · Why

Today the RSS feed has a one-line description ("Articles you shared, narrated.") and no cover art at all. In a podcast app library, the show appears as a generic grey square with no visual identity. Users who subscribe in Apple Podcasts or similar see something that doesn't look like a real product.

Fixing this is a few lines of XML plus one image. Disproportionate UX upside for the effort.

2 · What we're building

  1. A single, brand-wide cover image rendered at 3000×3000 JPG (Apple's max recommended size for retina podcast displays), generated from a small Python script and committed to the repo as a binary.
  2. A new route GET /cover.jpg that serves the image with long Cache-Control.
  3. Three new XML elements in templates/feed.xml: an updated <description>, an <itunes:summary> (same text — some apps prefer this), and an <itunes:image> at channel level.

The cover art is the same for every user — the feed is privately scoped per-user but the brand is one thing. No per-user customization.

4 · RSS additions

Description text

Chosen via terminal Q&A: Your personal podcast of articles you've saved with Feed Me.

Used verbatim in both <description> and <itunes:summary>.

New / changed XML

Diff to templates/feed.xml — inside <channel>, add (or update) these elements alongside the existing ones:

<description>Your personal podcast of articles you've saved with Feed Me.</description>
<itunes:summary>Your personal podcast of articles you've saved with Feed Me.</itunes:summary>
<itunes:image href="{{ cover_url }}"/>

The existing <description> ("Articles you shared, narrated.") is replaced. The other channel-level elements (<title>, <link>, <language>, <itunes:author>, <itunes:explicit>) are unchanged.

What we are NOT adding

  • <itunes:type> — defaults to episodic which is what we want; explicit declaration not required
  • <itunes:category> — relevant only for discovery; we're a private feed
  • <itunes:owner> — would require an email address, which we deliberately don't collect
  • Per-episode <itunes:image> — channel image is sufficient; podcast apps inherit
  • <itunes:duration> — would require parsing each MP3; nice-to-have, out of v1.4

5 · Implementation notes

New files

  • scripts/gen_cover.py — Python script that uses Pillow to render static/cover.jpg. Run-once tooling; not invoked at request time.
  • static/cover.jpg — committed binary, ~100-300 KB.
  • tests/test_cover.py — route test for GET /cover.jpg.

Modified files

  • app.py — add the GET /cover.jpg route serving static/cover.jpg with Cache-Control: public, max-age=86400; also pass a cover_url into rss.render_feed.
  • rss.py — render_feed gains a cover_url: str keyword-only parameter, passed through to the template.
  • templates/feed.xml — add the three new XML elements above.
  • tests/test_rss.py — tests assert the new elements render with the right text/href.
  • pyproject.toml — Pillow added under [dependency-groups] dev (not a runtime dependency; only the script needs it).

Generator script

scripts/gen_cover.py is a small standalone script. Run with uv run --group dev python scripts/gen_cover.py — produces static/cover.jpg. Re-run when the design changes; commit both the script change and the regenerated image.

Sketch of the algorithm (full code in the plan):

  1. Create 3000×3000 RGB image, fill with the 160° gradient (vectorized; iterate rows mapped to gradient stops)
  2. Draw a filled black circle at center (410, 410) radius 205
  3. Draw a centered right-pointing triangle inside the circle in cream
  4. Draw "FEED" and "ME" as separate text lines anchored at bottom-left, using a bundled-with-Pillow bold sans font (DejaVu Sans Bold ships with Pillow's ImageFont.truetype("DejaVuSans-Bold.ttf", size))
  5. Save as JPG quality 90

Route

STATIC_DIR = Path(__file__).parent / "static"


@app.get("/cover.jpg")
def cover_route():
    return FileResponse(
        STATIC_DIR / "cover.jpg",
        media_type="image/jpeg",
        headers={"Cache-Control": "public, max-age=86400"},
    )

RSS render call

In the feed_route in app.py, pass the cover URL through:

xml = rss.render_feed(
    feed_url=f"{APP_BASE_URL}/u/{secret}/feed.xml",
    audio_base=f"{APP_BASE_URL}/u/{secret}/audio",
    cover_url=f"{APP_BASE_URL}/cover.jpg",
    episodes=eps,
)

The cover URL is brand-wide, not per-user; it points at the single static file.

Dockerfile

No change needed. The COPY . . step already includes the new static/ directory and the script. Pillow is dev-only so the production image stays slim.

6 · Testing

RSS tests (updated)

  • Update existing test_render_feed_has_required_structure to assert the new description text appears.
  • New: test_render_feed_includes_itunes_image_and_summary — pass a cover_url, assert that <itunes:image href="..."/> and <itunes:summary> both appear with the right values.

Cover route test (new file)

  • test_cover_route_returns_jpeg: GET /cover.jpg, assert status 200, content-type image/jpeg, body length > 1KB (sanity check that the bytes are real), Cache-Control header present.

Generator script (no test)

gen_cover.py is build-time tooling. Verified by eye against the spec before commit. If we want, a sanity check that the script exits 0 and produces a file >10KB could be added — but that just tests Pillow, not our design.

App-level test (no change needed)

Existing test_feed_xml_returns_valid_rss already asserts <rss is in the body. The new elements don't require new app-route tests because the RSS unit tests cover them; the app route is a thin pass-through.

7 · Out of scope

  • Per-user cover art. Friends share the same brand image. Custom uploads would require user-facing image management.
  • Per-episode cover art. Apps inherit the channel image; no need for per-episode overrides.
  • Per-episode duration. Would require parsing each MP3 (mutagen or similar); nice-to-have, not v1.4.
  • iTunes podcast category submission. The feed is private — Apple's category metadata is for the public directory.
  • Owner email. Deliberately not collected.
  • Settings page preview of the cover. Users see the cover in their podcast app; no need to render it on the web page too.

8 · Known follow-ups future

  • Per-episode duration. Parse MP3 length at ingest time, store in the episode JSON, render in <itunes:duration>. Useful UI for the podcast app's library view. Defer until a friend asks for it.
  • Per-user accent color or initial overlay on the cover. If a friend feels their feed looks identical to mine in a shared screenshot, we could generate a per-user JPG with a small monogram. Not worth doing now.

9 · Acceptance criteria

  • scripts/gen_cover.py committed; running it produces static/cover.jpg matching the locked design
  • static/cover.jpg committed (3000×3000, JPG, ~100-300 KB)
  • GET /cover.jpg returns 200 with image/jpeg content-type and a long Cache-Control
  • rss.render_feed accepts and renders cover_url into <itunes:image>
  • Description text in <description> and <itunes:summary> matches the chosen string
  • All existing tests still pass; new tests pass
  • Deployed to https://feed-me.xyz; curl https://feed-me.xyz/cover.jpg returns the JPG; curl https://feed-me.xyz/u/<secret>/feed.xml contains both the new description and <itunes:image href="https://feed-me.xyz/cover.jpg"/>
  • On a real podcast app (Apple Podcasts), refreshing/re-subscribing the feed shows the cover art and updated description
