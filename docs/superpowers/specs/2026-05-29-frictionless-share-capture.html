Spec · v3.0

Frictionless Share Capture

Feed Me · 2026-05-29 · spec

Today, getting an article into your feed costs a fragile setup: copy your per-user ingest URL, install an iCloud Shortcut, then paste the URL into an import prompt. It's buried under "More" in the share sheet, and it silently breaks the moment you rotate your secret. This spec replaces that front door with one generic Shortcut — no secret baked in, one-tap install, zero paste — that opens /share?url=… in Safari, where a long-lived first-party cookie identifies you. The entire ingest pipeline (fetch → TTS → RSS → storage) is untouched; only the capture front door changes.

No backward compatibility. Nobody is using the current build, so the per-user /u/{secret}/ingest route and the entire copy/paste install flow are deleted, not deprecated. There is no transition story.

1 · Why

The concept is strong but the plumbing is user-hostile. The pain isn't the steady-state tap count — once the Shortcut is pinned, sharing is ~2 taps. The pain is three specific things:

  1. The copy/paste install. Each user must paste a personal ingest URL into an import prompt. Error-prone and bewildering.
  2. Discoverability. The Shortcut hides under "More" until manually pinned.
  3. Rotation breakage. Rotating the secret silently breaks the saved Shortcut, with no signal to the user.

The root cause of #1 and #3 is the same: the per-user secret is embedded in the Shortcut. Pull the secret out of the Shortcut and into a browser cookie, and the Shortcut becomes generic — installable in one tap, identical for everyone, and immune to rotation.

We also considered a native app with a Share Extension (best-possible capture) and an email/messaging on-ramp (zero install). Both were rejected for now — see Out of scope and Known follow-ups. The decisive argument against the native app: its marquee feature would be an in-app player, but Feed Me's whole premise is that articles land in the podcast app you already use. A standalone player fights that premise. Stripped of the player, a native app is just a Share Extension behind App Store review — not worth the standing tax.

2 · What we're building

Three changes, all inside the existing FastAPI app. No new services, no new dependencies.

  1. New route GET /share?url=… — the generic Shortcut's target. Reads the session cookie to learn who you are, spawns the existing ingest pipeline, and returns an HTML confirmation page ("🎧 Added!").
  2. A long-lived session cookie. Set on every GET /u/{secret} page view (which the /create flow and every revisit already pass through). The cookie value is the secret.
  3. One generic Shortcut + settings-page cleanup. A single iCloud Shortcut for all users (Open URL → /share?url=<input>). The settings page drops the clipboard/paste dance entirely; "install" becomes one tap.

Deleted:

  • GET /u/{secret}/ingest route in app.py removed
  • The ingest_url context variable + installShortcut()/copyIngestUrl() clipboard JS in settings.html removed
  • The "Ingest URL" block in the Settings drawer removed

3 · The capture flow

Cookie lifecycle

  • Set / refresh: on GET /u/{secret}, the response carries Set-Cookie: fm_session=<secret>. Because /create 303-redirects there, and rotation 303-redirects to the new feed page, this single touch-point covers create, revisit, and rotation.
  • Attributes: HttpOnly, Secure (prod only — see impl), SameSite=Lax, Max-Age = 1 year, Path=/.
  • Why these: server-set (not JS) dodges Safari's 7-day ITP cap on script cookies. SameSite=Lax is sent on the top-level GET navigation that "Open URLs" performs. HttpOnly keeps the secret out of JS — arguably safer than today's URL-in-history.

/share behavior

ConditionResponse
Valid cookie + valid url Quick fetch_title (typically ~1s, 5s timeout), write pending episode, spawn ingest, render "🎧 Added: <title>" page (200). This is the near-instant confirmation the product lacks today.
Valid cookie + missing/invalid url Mirror the old /ingest behavior: write_failed_episode so the failure is visible on the feed page, render an error variant (200).
No cookie / stale secret (dir gone) Render a "connect this browser" page (200): "Open your Feed Me page in this browser once, then share again." No episode written.

All branches return 200 with HTML — the Shortcut opens this in Safari, so a clean page beats an HTTP error. "Stale secret" (cookie points at a rotated-away secret) is treated identically to "no cookie".

The one assumption everything rests on

A Shortcut's "Open URLs" action must open Safari carrying the first-party feed-me.xyz cookie. This is distinct from "Get Contents of URL" (a background fetch with its own cookie jar — which is exactly why a silent background POST won't work and we must visibly open Safari). High-confidence, but unverified on-device — hence the spike below.

4 · Step zero: the cookie spike do this first

Before building anything else, prove the assumption on a real phone against prod (it cannot be reproduced in TestClient: it needs real Safari, the Secure flag, and the Shortcuts "Open URLs" path).

  1. Add the Set-Cookie line to GET /u/{secret}.
  2. Add a stub GET /share that renders only: cookie seen: yes (secret=…) or cookie seen: no.
  3. Deploy to Fly. Build a one-action Shortcut: Open URL → https://feed-me.xyz/share.
  4. On iPhone: open your feed page in Safari (sets the cookie) → run the Shortcut.

Green light: /share reports cookie seen: yes → build the full feature. Red light: the cookie doesn't arrive → stop and reconsider capture (fallback options: re-embed a token via "Get Contents of URL", which reintroduces the paste; or pivot to the email/messaging on-ramp). Either way we've spent ~15 minutes, not a full build.

5 · Implementation notes

Cookie helper + setting it on the feed page

COOKIE_NAME = "fm_session"
COOKIE_MAX_AGE = 60 * 60 * 24 * 365          # 1 year
COOKIE_SECURE = APP_BASE_URL.startswith("https")  # False on localhost/tests

def set_session_cookie(response, secret: str) -> None:
    response.set_cookie(
        COOKIE_NAME, secret,
        max_age=COOKIE_MAX_AGE, httponly=True,
        secure=COOKIE_SECURE, samesite="lax", path="/",
    )

In settings(): build the TemplateResponse as today, call set_session_cookie(resp, secret), return it. Gating Secure on the https scheme keeps the cookie working under Starlette's TestClient (http), so the cookie-path tests are real.

New /share route (replaces ingest_route)

@app.get("/share", response_class=HTMLResponse)
def share_route(request: Request, url: str = ""):
    secret = request.cookies.get(COOKIE_NAME)
    if not secret or not storage.user_exists(DATA_DIR, secret):
        return templates.TemplateResponse(
            request, "share.html", {"state": "connect"})
    parsed = urlparse(url)
    if not url or parsed.scheme not in ("http", "https") or not parsed.netloc:
        error_msg = ("Shortcut sent no article URL." if not url
                     else f"Invalid URL: {url[:200]!r} — must be http or https.")
        storage.write_failed_episode(
            DATA_DIR, secret,
            source_url=(url or "(empty share)"), error=error_msg)
        return templates.TemplateResponse(
            request, "share.html", {"state": "error", "error": error_msg})
    title = ingest.fetch_title(url)
    slug = storage.write_pending_episode(
        DATA_DIR, secret, source_url=url, title=title)
    spawn_ingest(url, secret, DATA_DIR, slug)
    return templates.TemplateResponse(
        request, "share.html",
        {"state": "added", "title": title or hostname(url)})

Side-effect-on-GET matches the existing house pattern (the old /ingest was also a GET). The bad-URL handling is lifted verbatim from ingest_route, minus the per-secret path param.

New template: templates/share.html

One small page with a state switch (added / error / connect), styled to match landing.html. Content:

  • added: "🎧 Added to your feed" + the title + a line: "Ready in your podcast app in 1–2 min. You can close this tab."
  • error: the error message + "Try sharing again."
  • connect: "This browser isn't linked to a feed yet. Open your Feed Me page (the link you bookmarked) in this browser once, then share again."

settings.html changes

  • Step 2 ("Install the iOS Shortcut"): drop the clipboard prelude. New desc: "One tap — no copy/paste. The same Shortcut works for everyone; it knows it's you because this browser is linked to your feed." Button becomes a plain link to shortcut_url (no onclick).
  • Step 3 of "Share an article": replace "Wait 1–2 minutes…" with "Safari shows 🎧 Added! instantly; the episode lands in your podcast app within 1–2 min."
  • Settings drawer: delete the entire "Ingest URL" block (label, pill, copy button).
  • <script>: delete INGEST_URL, INGEST_URL_WITH_PARAM, installShortcut(), copyIngestUrl(). Keep copyFeedUrl() and SHORTCUT_URL/FEED_URL.

settings() route change

Drop the ingest_url context var (and its construction). Keep feed_host_and_path (still used by the Apple Podcasts deep link). Set the session cookie on the response.

6 · Testing

Follow the existing tests/test_app.py patterns. The project is TDD — write these first.

New app tests

  • test_settings_sets_session_cookie — GET /u/{secret} response sets fm_session = the secret.
  • test_create_links_browser — POST /create following the redirect leaves fm_session set on the client.
  • test_share_with_cookie_spawns_ingest — client carrying a valid fm_session; monkeypatch app.spawn_ingest + ingest.fetch_title; GET /share?url=https://example.com/a returns 200, writes a pending episode, page contains "Added".
  • test_share_without_cookie_shows_connect — no cookie → 200, contains the connect prompt, no episode written.
  • test_share_bad_url_writes_failed — valid cookie, empty/invalid url → a Failed episode is written and the error page renders.
  • test_share_stale_secret_shows_connect — cookie set to a secret whose dir doesn't exist → connect prompt, no write.
  • test_old_ingest_route_gone — GET /u/{secret}/ingest?url=… returns 404.

Existing tests to update

  • test_settings_renders_for_known_user asserts f"/u/{secret}/ingest" in response.text and "Install Shortcut". Update: the ingest URL no longer appears; the button label/flow changed. Re-point these assertions at the new one-tap copy.
  • Any test exercising /u/{secret}/ingest directly → rewrite against /share with a cookie, or delete.

7 · Out of scope

  • Login / magic-link auth. Account model is unchanged: the bookmarked feed URL is the account; recovery = reopen the link. The pain the user explicitly de-prioritized; adding auth here is YAGNI.
  • Email / messaging capture (option B). A second on-ramp with its own infra and spam surface. Not now.
  • Native app + Share Extension (option C). Rejected: the player fights the "listen in your existing podcast app" premise; the rest is App Store overhead.
  • Silent (no-Safari-flash) ingest. Would require re-embedding a token in the Shortcut — i.e. the paste we're deleting. The flash is a feature here: it's instant confirmation.
  • Cross-browser linking. You link a browser by opening your feed page in it. No sync beyond that.

8 · Known follow-ups future

  • Revisit C only if the Safari flash annoys in daily use and a native extension is the sole fix. We'll know within a week of living on this. If pursued, ship via App Store (not TestFlight — external builds expire every 90 days).
  • Email / messaging on-ramp (B) as an additive channel for people who'd rather not touch Shortcuts.
  • Magic-link login for real multi-device + recovery, if the secret-URL model starts hurting.
  • Nicer return-to-article after share. Safari can't be force-closed from a page; explore the smoothest "you're done" affordance.

9 · Acceptance criteria

  • Installing capture = tapping one Shortcut link. No copy/paste anywhere in the flow.
  • Sharing an article opens Safari to a "🎧 Added!" confirmation within a second or two (a quick title fetch, then the page).
  • The same generic Shortcut works for any user; identity comes only from the cookie.
  • A browser that has visited its feed page shares successfully; one that hasn't sees the connect prompt (no crash, no error code).
  • Rotating the secret, then visiting the new feed page, re-links the browser; sharing still works. No manual Shortcut reinstall.
  • GET /u/{secret}/ingest returns 404.
  • The settings page shows no ingest URL and no paste step.
  • All tests pass; old ingest/paste tests are updated or removed.
