The Producer

Feed Me · 2026-08-26

The product's core loop: the user listens in their native podcast app on the go; the agent's job is building the feed. This release strengthens and closes that loop by making the agent the feed's producer: it explains its picks in the show notes, takes standing assignments from the user, and hears back from the listening moment itself. Three mechanics, shippable in order.

1 · Producer's notes

  • POST /u/<secret>/episodes (both modes) accepts an optional string note (cap 300 chars, 400 on wrong type or over-length): one line to the listener about why the producer picked this.
  • Stored on the pending record; write_episode / write_failed_episode preserve it the way they preserve via (generalize _pending_via to read the prior record once).
  • RSS: the episode description leads with Producer's note: <note> (HTML and text variants), before the excerpt.
  • Page: the episode row shows the note as a quiet line under the title.
  • WebMCP: add_article / add_article_text schemas gain note. Spoken intros: explicitly out of scope this release.

2 · The assignment desk

  • Storage: <user>/inbox/requests.json (a subdirectory, invisible to the episode glob and un-deletable via the episode DELETE). Entries: {id, text, ts, status: open|done, source: owner|listener, done_ts?, done_note?}. Caps: 500 chars per request, 20 open per feed. add_request dedupes an open request with identical text (returns the existing one). New storage functions: list_requests, add_request, complete_request.
  • Page: a "For your producer" card after the episodes: one-line form (placeholder "e.g. Something on the Ottoman Empire this week"), open requests listed beneath (listener feedback marked), the last few completed shown muted with the producer's done_note when present. Form posts text urlencoded and redirects 303 back. Fragment served at GET /u/<secret>/requests_partial so tools can refresh it (id requests-section).
  • API (path-secret, agent contract, JSON errors): GET /u/<secret>/requests → open requests plus the last 5 done; POST /u/<secret>/requests (JSON or form; form redirects, JSON returns 201); POST /u/<secret>/requests/<id>/complete with optional note → {"id","status":"done"}, 404 unknown.
  • Tools: get_requests (description says to call it at the start of any session on this page) and complete_request({id, note?}); both flash/refresh the requests card.

3 · Loop-back from the podcast app

  • Each RSS episode description ends with two plain links: More like this → {feed_page}/feedback?slug=<s>&v=more and Not for me → …&v=less.
  • GET /u/<secret>/feedback records a listener request (More like "<title>" / Fewer like "<title>", source listener, deduped while open) and renders a tiny confirmation page: "Noted. Your producer will see this." No GA on this page (the URL carries the secret); unknown slug or bad v → 404.

4 · Producer framing

  • Trace copy: "your producer is adding an article...", "your producer created this feed", etc.
  • AGENTS.md: frames the agent as the feed's producer, documents note, the requests API, both new tools, and example prompts.
Constraints: no em-dashes in any user-facing copy; request text is user/listener input, rendered only through Jinja autoescape and never into RSS; the raw secret stays out of analytics (requests routes attribute by hash or not at all); analytics.track never raises on the new routes. Requests live outside the episode namespace by construction.

5 · Acceptance

  • An episode created with a note shows it on the page and leads with it in the show notes; the note survives pending → ready and pending → failed.
  • The user can leave a request on the page; an agent can list it and complete it with a note; the card reflects both without a reload when done via tools.
  • Tapping a show-notes feedback link records a deduped listener request and confirms quietly.
  • Full suite green; CHANGELOG v3.36 + tag; deployed and verified.
