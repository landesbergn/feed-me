Spec · v3.1

Basic Analytics

Feed Me · 2026-06-02 · spec

Add lightweight, self-hosted analytics so the owner can see site traffic, how many feeds exist, how many articles get shared, and per-feed activity. Events are stored in a SQLite database on the Fly volume (Python standard library, no new dependency, no third party, no free-tier limit) and surfaced through a token-protected stats page and a JSON export designed to be analyzed later with Claude (SQL-friendly, fetchable).

Privacy guarantee. The per-feed identifier is a one-way sha256(secret)[:12] hash, never the secret itself. The analytics data can therefore never reveal a private feed URL. No IP addresses, user-agents, or other PII are stored — only the event name, hashed feed id, a coarse path label, and a timestamp.

1 · Why

The owner wants to know whether anyone is using Feed Me: visits, feeds created, articles shared, and which feeds are active. PostHog is out (the owner's one free project is already used). The app is privacy-forward and minimalist, so the analytics must add no third-party request, no new dependency, and must not weaken the "private feed" promise. The data should also be easy to analyze later with Claude, which favors a structured, SQL-queryable store.

2 · What we're building

  1. New module analytics.py (stdlib sqlite3 only): a SQLite events store with feed_hash(), track(), and summary().
  2. Instrumentation in app.py: four events — page_view, feed_created, article_shared — each tagged with the hashed feed id when known.
  3. Two token-protected admin routes: GET /admin/stats (HTML summary) and GET /admin/export (JSON of summary + raw events).

3 · Data model

SQLite DB at DATA_DIR/_analytics/analytics.db (on the Fly persistent volume, survives deploys). It lives in its own subdirectory on purpose: the /data/<secret>/ feed level stays pure, so any current or future "list feeds" code can keep assuming every entry there is a feed dir. (The DB also creates -wal/-shm sidecar files; keeping them out of /data/ root avoids inflating any feed count.) _connect() creates the _analytics/ dir if missing. Single table:

CREATE TABLE IF NOT EXISTS events (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    ts        INTEGER NOT NULL,         -- unix seconds
    event     TEXT    NOT NULL,         -- 'page_view' | 'feed_created' | 'article_shared'
    feed_hash TEXT,                     -- sha256(secret)[:12], or NULL when no feed context
    path      TEXT,                     -- coarse label: 'landing' | 'settings' | 'share'
    props     TEXT                      -- optional JSON string, NULL by default
);
CREATE INDEX IF NOT EXISTS idx_events_event ON events(event);
CREATE INDEX IF NOT EXISTS idx_events_ts ON events(ts);

"Number of feeds" and "number of articles shared" can also be cross-checked against the filesystem (count of user dirs; count of episode JSONs). The summary() uses the events table as the source of truth for time-series, and the route may add the live filesystem feed count as a sanity total — if it does, it MUST filter to directories ([p for p in DATA_DIR.iterdir() if p.is_dir()]), never a raw iterdir() count, so the _analytics/ dir and any future non-feed entries don't skew the number.

4 · The analytics module

Connection & init

Open a short-lived connection per write/read (the app is low-traffic; this avoids cross-thread connection issues, since ingest runs in background threads — do not later "optimize" into a shared module-level connection, which the daemon ingest threads would make unsafe). _connect() creates the parent _analytics/ dir (mkdir(parents=True, exist_ok=True)) and the schema on first use. The DB path is passed in (built from app.DATA_DIR at call time) so tests can point it at a temp dir. Enable WAL for safe concurrent reads.

feed_hash

import hashlib

def feed_hash(secret: str) -> str:
    """One-way, truncated. Stable per feed, never reversible to the secret."""
    return hashlib.sha256(secret.encode()).hexdigest()[:12]

track

def track(db_path, event, *, feed_hash=None, path=None, props=None, ts=None):
    """Insert one event. MUST never raise — analytics can't break a page render."""
    try:
        conn = _connect(db_path)          # ensures schema exists
        with conn:
            conn.execute(
                "INSERT INTO events (ts, event, feed_hash, path, props) "
                "VALUES (?, ?, ?, ?, ?)",
                (ts or int(time.time()), event, feed_hash, path,
                 json.dumps(props) if props else None),
            )
        conn.close()
    except Exception:
        pass  # swallow — never propagate analytics failure to the request

summary

def summary(db_path) -> dict:
    """Aggregate counts for the stats page / export."""
    # Returns a dict like:
    # {
    #   "feeds_created": int,            # COUNT events WHERE event='feed_created'
    #   "articles_shared": int,          # COUNT events WHERE event='article_shared'
    #   "page_views": int,               # COUNT events WHERE event='page_view'
    #   "page_views_by_path": {landing, settings, share},
    #   "active_feeds": int,             # COUNT(DISTINCT feed_hash) WHERE feed_hash NOT NULL
    #   "by_day": [{"day": "2026-06-02", "page_views": n, "shares": n, "feeds": n}, ...],
    #   "top_feeds": [{"feed_hash": "...", "shares": n}, ...]  # by article_shared, top 20
    # }

All aggregation is plain SQL (GROUP BY, COUNT, strftime('%Y-%m-%d', ts, 'unixepoch')). No external query layer.

5 · Instrumentation

A thin helper in app.py keeps call sites one line and centralizes the hashing: 

def _analytics_db():
    # Built at call time, not module load, so tests that monkeypatch DATA_DIR
    # (and the per-request DATA_DIR) resolve to the right path.
    return DATA_DIR / "_analytics" / "analytics.db"

def _track(event, *, secret=None, path=None, props=None):
    analytics.track(
        _analytics_db(), event,
        feed_hash=analytics.feed_hash(secret) if secret else None,
        path=path, props=props,
    )

Call sites:

  • landing() → _track("page_view", path="landing")
  • settings() → _track("page_view", secret=secret, path="settings")
  • share_route() (added branch only) → _track("page_view", secret=secret, path="share") and _track("article_shared", secret=secret, path="share")
  • create() → after the user is made, _track("feed_created", secret=secret)

The DB schema is created lazily on first track()/summary() via _connect(), so there is no startup ordering dependency. Because track() swallows all exceptions, none of these call sites can fail a request.

6 · Admin access

A single secret, the STATS_TOKEN environment variable (set as a Fly secret), gates both admin routes. The guard must short-circuit before hmac.compare_digest (which raises on a None argument): 

STATS_TOKEN = os.environ.get("STATS_TOKEN")

def _check_token(token: str):
    if not STATS_TOKEN or not token or not hmac.compare_digest(token, STATS_TOKEN):
        raise HTTPException(404)   # 404, not 401/403 — reveal nothing

So an unset STATS_TOKEN, a missing ?token=, or a wrong token all yield 404 (not 401/403 — reveals nothing about the route's existence).

  • GET /admin/stats?token=… → small HTML page rendering summary(): headline counts, a by-day table, page-views-by-path, and the top active feeds (by hashed id).
  • GET /admin/export?token=… → JSONResponse with {"summary": …, "events": […]} (all rows). Designed so a future Claude session can WebFetch it with the token, or the owner can download and hand it over. Add ?since=<unix> later if the table grows; not needed now.

7 · Testing

Follow the existing tests/ patterns (pytest, the client fixture monkeypatches DATA_DIR to a tmp dir, so analytics.db lands there).

analytics module (new tests/test_analytics.py)

  • feed_hash is stable, 12 chars, and never equals the input secret.
  • track then summary returns the right counts for each event type.
  • summary active_feeds counts distinct non-null feed hashes.
  • track on an unwritable/invalid path returns without raising (defense-in-depth).

app instrumentation (in tests/test_app.py)

  • POST /create records exactly one feed_created.
  • A successful /share records an article_shared with the sharer's feed hash.
  • GET / records a page_view with path="landing".
  • Analytics failure can't 500 a page: monkeypatch analytics.track to raise, assert / still returns 200. (Belt-and-suspenders alongside the in-module swallow.)

admin routes (in tests/test_app.py)

  • /admin/stats and /admin/export with no token → 404.
  • With a wrong token → 404.
  • With the correct token (set STATS_TOKEN via monkeypatch) → 200; export JSON contains the recorded events and a summary.

8 · Out of scope

  • Ingest success/failure events. Only shares are tracked for now; whether the audio later succeeds is a separate future event.
  • Charts / dashboards. The stats page shows tables and counts, not graphs.
  • Real-time updates. The stats page is a plain render; refresh to update.
  • IP / geo / user-agent / referrer capture. Deliberately not stored (privacy).
  • Retention/cohort analysis. The raw export enables it later with Claude; not built in.

Caveat — bot inflation on page_view. Since v3.0 ships Open Graph tags, link-unfurl bots (iMessage, Slack, etc.) and iOS icon probes fetch /, so the landing page-view count will run noisy/high and should not be read as real humans. Acceptable for "basic" analytics; a future tweak could skip obvious bot user-agents at track() time (checked, not stored). The feed_created and article_shared counts are unaffected (bots don't POST or share).

9 · Acceptance criteria

  • Visiting the landing, a feed page, and sharing an article each write the expected event rows to analytics.db.
  • Every stored event that has feed context carries sha256(secret)[:12]; the raw secret never appears in the DB or export.
  • /admin/stats?token=… shows total feeds, total articles shared, total + per-path page views, by-day activity, and top feeds by share count.
  • /admin/export?token=… returns JSON (summary + events) suitable for later analysis.
  • Both admin routes return 404 without the correct token; STATS_TOKEN unset also yields 404.
  • A failure inside analytics never changes a user-facing response (pages still 200).
  • No new runtime dependency is added; all existing tests plus the new analytics/admin tests pass.
