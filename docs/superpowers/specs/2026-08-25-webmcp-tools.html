Spec · v3.28

WebMCP tools

Feed Me · 2026-08-25 · spec

Let an agent that lives in the browser (ChatGPT's browser, or Chrome with WebMCP enabled) drive Feed Me without reading AGENTS.md at all: when such an agent opens the landing page or a feed page, the page itself registers tools for creating a feed, narrating an article, checking progress, and managing episodes. One new static script, one new route, and a few lines of copy. No backend behavior changes.

1 · Why

Feed Me already meets agents where they are twice over: AGENTS.md plus the secret-authed JSON API for agents in terminals, and the pasted prompt on the feed page for chat agents. WebMCP is the third surface, and the one browsers are converging on: a page calls modelContext.registerTool(...) and an agent browsing that page discovers typed tools instead of guessing its way through the UI.

For Feed Me the fit is unusually clean:

  • The capabilities already exist. Every tool below maps to a shipped endpoint (POST/GET/DELETE /u/<secret>/episodes*, /voice, POST /create). The WebMCP layer is a thin same-origin fetch wrapper.
  • The auth model gets better, not worse. The page already knows the secret (it is the URL); the tools call same-origin endpoints; the agent never has to be handed the credential out of band or persist it. The "Step 0 · Remember this feed" dance (v3.12) becomes unnecessary in a WebMCP browser: being on the page is the credential.
  • Immediate occasion: the OpenAI WebMCP Challenge (submissions close Sep 3, 2026), which wants exactly this: a live site whose existing product becomes agent-drivable. The repo work here stands on its own; the hackathon submission itself is out of scope (§8).

2 · What we're building

  1. A new committed static asset static/webmcp.js that feature-detects the WebMCP API and registers tools: the full set on the feed page (/u/<secret>), create_feed alone on the landing page (/). No-op everywhere the API is absent, so ordinary browsers are untouched.
  2. A new route GET /webmcp.js serving that file as text/javascript (static assets are served by explicit routes in this app; there is no StaticFiles mount).
  3. Script includes (<script src="/webmcp.js" defer>) on landing.html and settings.html only.
  4. Copy: one sentence in the "For your agent" panel, a short "In a browser (WebMCP)" section in AGENTS.md, a line in llms.txt, README route row and mention, CHANGELOG v3.28.

No change to any endpoint, the rate limiter (WebMCP shares flow through the existing agent API and its 5/day cap and character budget), storage, RSS, or GA masking.

3 · The tools

Feed page (/u/<secret>)

ToolInputBacked byNotes
add_article{url} POST /u/<s>/episodes (URL mode) Returns the 202 body (slug, status, remaining) plus a reminder to poll.
add_article_text{text, title, url?} POST /u/<s>/episodes (text mode) The killer path for browser agents: text the agent already has (its own research, a page a server fetch cannot reach) becomes an episode with no fetch.
list_episodesnone GET /u/<s>/episodes Returns the JSON body verbatim (20 most recent, voice, remaining, budget).
get_episode_status{slug} GET /u/<s>/episodes/<slug> Description tells the agent to poll no faster than every few seconds.
delete_episode{slug} DELETE /u/<s>/episodes/<slug> Description says it is irreversible and to confirm with the user before deleting anything they did not just ask to remove.
set_voice{voice} (enum: alloy, echo, nova, shimmer) POST /u/<s>/voice (form) Success is the status code; the tool answers "Voice set to X".
get_feed_infonone none (built from location) Feed page URL, private RSS URL, docs URL. Description says to treat both URLs as secrets.

Landing page (/)

ToolInputBacked byNotes
create_feednone POST /create The fetch follows the 303 to the new feed page (setting the session cookie); the tool reports the new page URL, then navigates there after a short delay so the result reaches the agent before the page unloads. On the feed page the full toolset registers. Description warns not to call it for a user who already has a feed.

Result and error shape

  • Every execute resolves to the MCP-style {content: [{type: "text", text: ...}]} object (the shape in the W3C proposal and the WebMCP examples).
  • JSON endpoint bodies pass through verbatim, so the agent sees the same fields AGENTS.md documents. Non-2xx responses become "Error <status> (<code>): <message>" from the endpoint's own {"error","message"} body, falling back to "Error <status>." when the body is not that shape (e.g. the voice route's FastAPI 400). The API's existing rate-limit and budget messages are already agent-directed prose; they pass through untouched.

4 · The script and how it loads

  • Feature detection, both API homes: the W3C proposal puts the API at navigator.modelContext; current Chrome docs put it at document.modelContext. The script tries both (navigator first, matching the proposal) and returns silently when neither exists. It prefers per-tool registerTool and falls back to provideContext({tools}). The whole registration is wrapped in try/catch: an API-shape drift must never break the page.
  • Page detection: the secret comes from location.pathname matching /u/<secret> exactly (the same [A-Za-z0-9_-]+ alphabet as the slugs); the landing page is pathname === "/". Any other page registers nothing, so the script is inert if it is ever included elsewhere.
  • Loading: <script src="/webmcp.js" defer> just before </body> in landing.html and settings.html. Not on the share pages (transient, no toolset worth offering) and not on the admin page.
  • Serving: a GET /webmcp.js route returning FileResponse(STATIC_DIR / "webmcp.js", media_type="text/javascript"), following the _icon pattern. The file is committed, not generated; no scripts/gen_* involvement.
API-drift risk, named: WebMCP is an origin trial; the return shape and the API home have both moved between drafts. That is why the script (a) detects both homes, (b) supports both registration calls, and (c) never lets a registration failure escape. Before any public submission the owner should verify once against a real WebMCP browser; every likely drift is a one-line fix in static/webmcp.js.

6 · Security notes

  • No new exposure of the secret. Tools run in the page at /u/<secret>; a browser agent on that page can already read the address bar. All fetches are same-origin; the secret is sent nowhere new. get_feed_info returns the secret-bearing URLs on purpose (subscribing is the product) with a treat-as-secret warning in the description, mirroring the Auth section of AGENTS.md.
  • Caps unchanged. WebMCP shares hit POST /u/<s>/episodes and count against the existing agent cap (5/day) and per-feed character budget; the suspended-feed check applies. No new spend surface.
  • Analytics: the script makes no analytics calls and GA masking is untouched. Server-side tracking of the underlying endpoints stays exactly as it is (the agent API attributes by feed_hash, never the raw secret).
  • Prompt-injection surface: tool inputs go into JSON bodies or a form field, never into HTML; the page renders nothing from tool calls. Episode titles from agents were already possible via the agent API and are already escaped where shown.

7 · Testing

TDD, no network, existing client fixture. The JS cannot execute under pytest, so the JS logic stays simple and the tests pin the contract: the file is served correctly, the right pages load it, and the toolset and copy stay what this spec says. New file tests/test_webmcp.py:

  • Served: GET /webmcp.js → 200, content-type starts with text/javascript, body mentions modelContext, registerTool, and provideContext.
  • Toolset pinned: the body contains each tool name (add_article, add_article_text, list_episodes, get_episode_status, delete_episode, set_voice, get_feed_info, create_feed).
  • Included where it should be: the landing page and a feed page each contain src="/webmcp.js"; the share page does not.
  • Copy guards: no em-dash in webmcp.js; the agent panel contains the new WebMCP line; AGENTS.md contains "In a browser (WebMCP)" and the tool names, still substitutes {base}, still no em-dash (existing test already guards); llms.txt mentions WebMCP.
  • Inert elsewhere: static assertion that the script guards on pathname (the regex and the "/" check are present), the honest limit of DOM-less testing.

Manual verification (owner, once, before any submission): open the deployed landing page in a WebMCP-enabled browser, have the agent create a feed, add an article by URL and by text, poll to ready, list, set voice, delete.

8 · Out of scope

  • The hackathon submission itself: the Devpost entry, demo video, and write-up; a Chrome origin-trial token for feed-me.xyz (owner registration; judges can also enable the flag); any temporary cap raise for judging week. All owner decisions, separate from this change.
  • Tools on the share pages or admin page.
  • Cookie-authed tools for a returning visitor on the landing page (the cookie is HttpOnly and the flows are HTML-shaped; create_feed plus navigation covers the demo path).
  • Cross-origin tool exposure (exposedTo / fromOrigins), toolchange events, dynamic re-registration when episodes change.
  • A JS test runner for the repo; the script stays simple enough that contract tests plus one manual pass carry it.

9 · Acceptance criteria

  • GET /webmcp.js serves the committed script as text/javascript; landing and feed pages include it with defer; share pages do not.
  • The script registers exactly the eight tools in §3, on the right pages, with agent-facing descriptions, MCP-shaped results, pass-through JSON bodies, and the documented error strings; it is a silent no-op in a browser without WebMCP and cannot throw out of registration.
  • AGENTS.md, the agent panel, llms.txt, and the README say WebMCP exists and where; no em-dash anywhere new.
  • Full suite green (uv run pytest); CHANGELOG v3.28 entry and v3.28 tag.
  • End-to-end (manual, owner): in a WebMCP browser, a fresh visitor's agent can create a feed, narrate an article by URL and by pasted text, watch it go ready, and read back the RSS URL, without ever being pasted a prompt or shown AGENTS.md.
