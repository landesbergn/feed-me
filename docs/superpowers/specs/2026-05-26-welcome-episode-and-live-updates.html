Spec · v1.5

Welcome Episode + Live Updates

Feed Me · 2026-05-26 · spec

Two coupled UX gaps. (1) a fresh feed is empty, and most podcast apps refuse to subscribe to an empty show — so the friend journey breaks halfway through setup. (2) after sharing an article the settings page doesn't update until manual refresh, so the friend doesn't know the share worked. Both fixes are small but make the first-run feel like a finished product.

1 · Why

Spec drops have been polish-heavy (cover art, redesign, copy) and the friend journey still has rough edges. Two specific failures that hurt:

  • A friend tap "Add to Apple Podcasts" right after creating their feed → Podcasts opens the show, but the show has zero episodes → Follow button is disabled or behaves weirdly. They bounce.
  • A friend shares an article → goes back to the settings page to check → sees nothing happen → refreshes → sees Pending → refreshes again → sees Ready. Felt clunky; they're not sure if it's working until they manually refresh twice.

2 · What we're building

  1. A pre-rendered welcome MP3 (~30s, OpenAI TTS, generated once via a script and committed to the repo). On POST /create, the server copies it into the new user's directory so their feed has one real episode from the moment it exists.
  2. A new partial-rendering route GET /u/<secret>/episodes_partial that returns just the HTML for the episode section. JS on the settings page polls every 3 seconds while the tab is visible and swaps the section in place.

The episode-section markup is extracted into a Jinja partial template that both the main settings render and the polling endpoint use — single source of truth.

3 · Welcome episode

Script

Welcome to Feed Me. This is your private podcast feed for articles you want to listen to instead of read. Open an article in Safari, tap Share, then tap Feed Me — a new episode shows up here in about a minute. Head back to your Feed Me page to set things up. Enjoy.

~50 words. At tts-1's pace this lands at roughly 30 seconds. Voice: shimmer (matches the default). Generated once via a one-time script; committed to repo at static/welcome.mp3.

Generation

New script scripts/gen_welcome.py calls the same OpenAI client the ingest pipeline uses. Requires OPENAI_API_KEY in the environment when run. Output: static/welcome.mp3 (~50–100 KB). Re-run when the script changes; commit script + new MP3 together.

Seeding on user creation

New storage function: 

def seed_welcome_episode(data_dir: Path, secret: str, welcome_audio: bytes) -> str:
    """Write a welcome episode (mp3 + json) into a new user's directory.
    Returns the slug."""
    slug = _new_slug()
    user_dir = data_dir / secret
    (user_dir / f"{slug}.mp3").write_bytes(welcome_audio)
    (user_dir / f"{slug}.json").write_text(json.dumps({
        "title": "Welcome to Feed Me",
        "url": "https://feed-me.xyz",
        "ts": int(time.time()),
    }))
    return slug

The POST /create route reads static/welcome.mp3 once at module load time (or per-request — small file, but cache at import) and calls seed_welcome_episode right after storage.create_user.

Rotate URL behavior

No special handling. rotate_secret renames the directory; the welcome episode (and any others) come along. The welcome appears once per user lifetime.

Why a real MP3, not a silent placeholder

Apple Podcasts and many other apps don't just need "an enclosure exists" — they prefer/expect actual playable audio. A silent 1-second MP3 satisfies most validators but a 30-second narrated welcome doubles as onboarding for friends who tap play. Same effort either way (the seeding code is identical); the welcome script is what changes.

4 · Live episode updates

Mechanism

3-second polling, JS-driven, server returns HTML.

  1. Extract the existing "Recent episodes" section from templates/settings.html into a new partial templates/_episodes_section.html. The partial owns the <h2>Recent episodes</h2>, the table, the status chips, and the empty state.
  2. settings.html wraps the include in <div id="episodes-section">{% include "_episodes_section.html" %}</div>.
  3. New route GET /u/<secret>/episodes_partial returns the partial rendered with the user's current episodes. Same enrichment as the main settings route (status field, when via relative_time).
  4. JS in settings.html polls every 3 s using fetch(), replaces #episodes-section's innerHTML with the response text. Skips the poll when document.hidden is true.
  5. Polling starts on page load and continues until navigation. Wakes back up on visibilitychange.

JS sketch

const POLL_INTERVAL_MS = 3000;
const EPISODES_URL = window.location.pathname + "/episodes_partial";
const target = document.getElementById("episodes-section");

async function refreshEpisodes() {
  if (document.hidden) return;
  try {
    const resp = await fetch(EPISODES_URL, { cache: "no-store" });
    if (!resp.ok) return;
    target.innerHTML = await resp.text();
  } catch (e) { /* silent — page still works */ }
}

setInterval(refreshEpisodes, POLL_INTERVAL_MS);
document.addEventListener("visibilitychange", () => {
  if (!document.hidden) refreshEpisodes();
});

Behavior on slow network or failed fetch

Errors are swallowed silently. The existing content stays in place. Next interval tries again. The page is fully functional without polling (the server-rendered initial state is always correct).

Status transitions visible to user

After the friend taps the Shortcut to share an article:

  • ~0–3 s: ingest endpoint hit → daemon thread spawns → writes pending stub
  • ≤ 3 s after that: poll fires → table swaps → row appears with Pending chip
  • ~30–60 s later: ingest completes → row promotes to Ready (or Failed)
  • ≤ 3 s after that: poll picks it up → chip updates

Total perceived latency from share to visual confirmation: under 6 seconds.

5 · Implementation notes

New files

  • scripts/gen_welcome.py — TTS the welcome script, save to static/welcome.mp3
  • static/welcome.mp3 — committed binary (~50-100 KB)
  • templates/_episodes_section.html — partial with the recent-episodes table + empty state

Modified files

  • storage.py — add seed_welcome_episode(data_dir, secret, welcome_audio) -> str.
  • app.py — at module load, read static/welcome.mp3 into a module-level constant WELCOME_AUDIO_BYTES; POST /create calls storage.seed_welcome_episode after storage.create_user; new route GET /u/<secret>/episodes_partial.
  • templates/settings.html — replace the inline "Recent episodes" block with <div id="episodes-section">{% include "_episodes_section.html" %}</div>, plus inline <script> polling block.
  • tests/test_storage.py — test for seed_welcome_episode.
  • tests/test_app.py — update test_post_create_makes_user_dir + test_settings_renders_for_known_user to reflect the welcome episode; new tests for GET /u/<secret>/episodes_partial.

Module-level welcome audio cache

app.py reads static/welcome.mp3 bytes once at import time: 

WELCOME_AUDIO_BYTES = (STATIC_DIR / "welcome.mp3").read_bytes()

The bytes are small enough (~50–100 KB) that holding one copy in memory is fine. This avoids a disk read per signup. STATIC_DIR already exists from v1.4.

Welcome episode `url` field

The episode JSON has a url field — for shared articles, this is the source URL. For the welcome, we set it to https://feed-me.xyz (the landing page). This shows up as the "source" line in the settings table; harmless and clickable.

Test data dir gotcha

Tests use a client fixture that monkey-patches app.DATA_DIR to tmp_path. The welcome MP3 lives in STATIC_DIR (the repo static dir), unaffected by the monkey-patch, so WELCOME_AUDIO_BYTES at import time is the real production file. Tests that create users will get real welcome audio seeded. This is fine; tests need to account for the fact that brand-new users have one episode (the welcome) rather than zero.

6 · Testing

Storage test (new)

def test_seed_welcome_episode_writes_mp3_and_json(tmp_path):
    secret = storage.create_user(tmp_path)
    slug = storage.seed_welcome_episode(tmp_path, secret, welcome_audio=b"FAKE")

    assert (tmp_path / secret / f"{slug}.mp3").read_bytes() == b"FAKE"
    meta = json.loads((tmp_path / secret / f"{slug}.json").read_text())
    assert meta["title"] == "Welcome to Feed Me"
    assert "error" not in meta
    assert "pending" not in meta

App tests (updated)

  • test_post_create_makes_user_dir: assert that a brand-new user dir contains both settings.json AND exactly one welcome episode (any *.mp3 file present, any *.json with title "Welcome to Feed Me").
  • test_settings_renders_for_known_user: after creation, assert the welcome episode title "Welcome to Feed Me" appears on the page (because the user has one episode by default).

App tests (new)

  • test_episodes_partial_returns_html: create a user, GET /u/<secret>/episodes_partial, assert 200, response text contains "Welcome to Feed Me" (because seeding ran) and includes the table markup (<table or "Recent episodes").
  • test_episodes_partial_404_for_unknown_user: GET on an unknown secret, assert 404.
  • test_episodes_partial_reflects_new_pending_episodes: create a user, write a pending episode via storage, GET the partial, assert the new title appears AND "Pending" appears.

Generator script (no test)

gen_welcome.py is build-time tooling. Verified by ear after running. No automated test.

7 · Out of scope

  • Per-friend welcome customization. One MP3 for everyone.
  • WebSocket / SSE. Polling is fine for the realistic load.
  • Removing the welcome from a user's feed. No UI for episode deletion; the welcome stays in their library forever (or until they unsubscribe).
  • Polling cadence configurability. Hardcoded 3s; not user-tunable.
  • Live updates of the Voice picker, ingest URL, etc. Only the episode section polls.

8 · Known follow-ups future

  • Per-episode duration tag. Was already a v1.4 known follow-up. Especially useful once friends have a real "Welcome" episode that's pre-known to be ~30 s — could special-case the duration in the seed metadata.
  • Smart polling cadence. Slow down to every 10s when no pending episodes; back to 3s on activity. Useful at higher friend counts.
  • "Remove from feed" per-episode. Useful when a friend wants to delete a botched share. Out of v1.5; raise when it actually bites.

9 · Acceptance criteria

  • static/welcome.mp3 committed; playing it speaks the script in §3
  • Creating a brand new feed (POST /create) results in exactly one episode in the user's directory titled "Welcome to Feed Me"
  • That feed's /u/<secret>/feed.xml contains the welcome as an item with a working enclosure URL
  • Subscribing to that feed in Apple Podcasts succeeds (Follow button enables)
  • Settings page polls /u/<secret>/episodes_partial every ~3s while tab is visible
  • After sharing an article via the Shortcut, the new "Pending" row appears in the table within ~3 seconds of polling without manual refresh
  • The "Pending" row transitions to "Ready" within ~3 seconds of ingest completing
  • All existing tests pass; new tests pass; tests that asserted "empty feed" or "len(eps) == 1" after only-share are updated to account for the welcome episode
  • Deployed to https://feed-me.xyz

Brainstormed via terminal Q&A on 2026-05-26. Welcome script, real-time mechanism, and rotate behavior all chosen explicitly. Visual companion not needed — both decisions were textual.
