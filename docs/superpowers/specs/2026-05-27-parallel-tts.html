Spec · v1.8

Parallel TTS

Feed Me · 2026-05-27 · spec

v1.7 fixed the silent audio truncation by chunking long articles into multiple TTS calls, but those calls run sequentially. A 50-minute article takes ~10 minutes to ingest. This spec parallelizes the calls so the same article finishes in roughly the time of the slowest single chunk — about 60-90 seconds.

1 · Why

Verified end-to-end: a 50,400-char Notion article takes 10:02 from share to ready (13 chunks × ~45s/chunk sequentially). The chunks are independent — each TTS call is a pure function of the chunk text plus voice. There's no reason to serialize.

OpenAI's rate limit for the user's billing tier is 50 req/min for tts-1. Even a worst-case 25-chunk article (100k char cap ÷ 4k chars/chunk) burst all at once is well under that ceiling. No bounded concurrency needed.

2 · What we're building

One change to synthesize() in ingest.py: replace the sequential for chunk in chunks: … loop with a ThreadPoolExecutor that issues all TTS calls in parallel and collects results in order via executor.map().

Naive byte concatenation of the returned chunks still produces a valid MP3 — same as v1.7. The fact that they were generated in parallel doesn't change the output.

3 · Implementation notes

Single change to synthesize

Replace the existing function in /Users/noah/Desktop/feed-me/ingest.py:

from concurrent.futures import ThreadPoolExecutor


def synthesize(text: str, voice: str) -> bytes:
    """Generate MP3 audio for the full text. Chunks at sentence boundaries
    and issues ALL TTS calls in parallel; returns the concatenated MP3 bytes."""
    chunks = chunk_text(text, TTS_CHAR_LIMIT)
    if not chunks:
        return b""

    def render_one(chunk: str) -> bytes:
        response = openai_client.audio.speech.create(
            model=TTS_MODEL,
            voice=voice,
            input=chunk,
        )
        return response.content

    # max_workers=len(chunks) → unbounded parallelism (one worker per chunk).
    # Even for a 100k-char article that's ≤25 concurrent calls, well under
    # OpenAI's 50 req/min rate limit for tier-1 paid accounts.
    with ThreadPoolExecutor(max_workers=len(chunks)) as pool:
        parts = list(pool.map(render_one, chunks))
    return b"".join(parts)

Order preservation

executor.map() returns results in the same order as inputs, regardless of completion order. The concatenated bytes are therefore in the right sequence — audio plays chronologically with the article body.

Failure behavior

If any single TTS call raises (network error, 429, etc.), pool.map() re-raises the first exception when its result is requested. The exception propagates out of the with block, then out of synthesize, into process's existing except Exception handler, which writes a failed episode. Other in-flight chunks finish their work but their results are discarded. Acceptable: failed audio is more useful (user sees the failure on the settings page) than partial audio.

Memory

25 concurrent chunks × ~4 MB MP3 each ≈ 100 MB peak. Comfortable on the 1 GB Fly machine.

Worker thread context

synthesize is called from process, which runs in a daemon thread spawned by /ingest. The ThreadPoolExecutor creates additional worker threads inside that daemon thread. Standard Python threading; no special handling needed.

4 · Testing

Existing tests still pass

  • test_synthesize_long_text_calls_tts_for_each_chunk — asserts each chunk triggers a TTS call and bytes concatenate. Still passes; the order of fake_openai.calls may differ from input order under parallelism, but the count and the byte concat assertion don't depend on order.
  • test_synthesize_short_text_calls_tts_once — 1 chunk → 1 worker → 1 call. Identical behavior.
  • All other process and ingest tests are unaffected (single-chunk happy path uses the same code).

Updated test for order preservation under parallelism

The existing long-text test asserts audio == fake_openai.audio_bytes * len(fake_openai.calls). This works because the fake returns the SAME bytes every time, so order is invisible. To verify order preservation under real parallelism, add one new test where each call returns distinguishable bytes per chunk content: 

def test_synthesize_preserves_chunk_order(monkeypatch):
    """Even when chunks complete out of order, output bytes are in input order."""
    import ingest

    # A fake that returns the chunk text itself as the "audio" so we can
    # verify ordering. Also adds variable delay to encourage out-of-order completion.
    import time
    class OrderFake:
        def __init__(self):
            self.calls = []
        @property
        def audio(self):
            return self
        @property
        def speech(self):
            return self
        def create(self, *, model, voice, input):
            self.calls.append(input)
            # Simulate variable latency: earlier chunks take longer than later ones
            # to encourage them to finish AFTER later chunks.
            chunk_index = int(input.split()[-1])  # last word is the chunk number
            time.sleep(0.05 * (5 - chunk_index))
            return type("R", (), {"content": input.encode("utf-8")})()

    fake = OrderFake()
    monkeypatch.setattr(ingest, "openai_client", fake)

    # Build a body with clearly distinguishable chunks. Each "sentence" ends with
    # a unique trailing number, and chunk_text will split between sentences.
    body = ". ".join([f"Chunk number {i}" for i in range(5)]) + "."
    audio = ingest.synthesize(body, "shimmer")

    # The bytes must read in input order, regardless of which TTS call finished first.
    assert audio.startswith(b"Chunk number 0")
    assert audio.endswith(b"Chunk number 4.") or audio.endswith(b"Chunk number 4")

(The exact assertion may need to be tweaked depending on how chunk_text splits the synthetic body — the goal is just to verify order survives parallelism.)

5 · Out of scope

  • Bounded concurrency / rate-limit retry. User is on tier-1 paid; 25 concurrent calls is under the 50 req/min limit. If we ever hit 429s we add backoff + retry then.
  • Progress UI during pending. Friend still just sees "Pending" until the whole article is done. Now Pending lasts 60-90s instead of 10 min, so the bar for progress UI is lower.
  • Async/await refactor. Using sync OpenAI client + ThreadPoolExecutor is simpler than rewriting synthesize as async. No benefit to async here.
  • Streaming MP3 to disk as chunks complete. All chunks still buffered in memory before writing. ~100 MB peak is fine.

6 · Known follow-ups future

  • Pending-row progress indicator. Even at 60-90s, "Pending" with no estimate is opaque. Could show "Generating chunk 7 of 13" or just an ETA. Would need a way to surface progress from the worker thread; trivially possible by writing intermediate state to the episode JSON.
  • Retry on 429. If parallelism + a higher-traffic future state ever starts hitting rate limits, add exponential backoff. Out of v1.8.
  • Stuck-Pending cleanup. Daemon worker threads die on machine restart; pending stubs from interrupted ingests live forever. Garbage-collect stuck Pendings older than ~5 min as Failed on startup. Independent v1.x.

7 · Acceptance criteria

  • Re-sharing the same Notion article that took 10:02 in v1.7 completes in < 2 minutes wall time on prod.
  • Order is preserved — the audio plays chronologically through the article.
  • All existing tests pass; one new test verifies order preservation under parallel completion.
  • No new dependencies. Just concurrent.futures.ThreadPoolExecutor from stdlib.

Decided via terminal Q&A on 2026-05-27. Unlimited concurrency chosen because worst-case chunk count (25) is well under the user's tier-1 rate limit (50 req/min). No retry, no bounded pool, no async — kept as minimal as the change permits.
