Spec · v3.14

Narrate supplied text

Feed Me · 2026-06-07 · spec

Let an agent send the full text of an article or email directly to the agent API, and narrate that text instead of fetching a URL. The motivating case is paywalls: a user who is a paying subscriber receives the complete article in their inbox, but a server-side browser fetch of the same article's URL sees only the free preview (the fetch carries none of the user's credentials). When the agent already holds the full text, it should hand that text to Feed Me rather than a link.

1 · Why

The existing url path fetches the article server-side (ingest.fetch_article) with a spoofed browser User-Agent. It has no subscriber cookies, so a gated publisher serves a preview, and Feed Me correctly refuses to narrate a stub (the paywall and minimum-length guards in ingest.py). That is the right behavior for a link, but it throws away a case the agent can handle: the user already received the full text by email as a paying subscriber. This spec adds a text path so the agent can pass that content straight through, bypassing the fetch entirely.

2 · What we're building

  1. A text mode on POST /u/{secret}/episodes: a body carrying text (and a required title, optional url) narrates that text directly, with no network fetch.
  2. ingest.process learns to narrate pre-supplied text: when given text it skips fetch_article (and the readability/trafilatura extraction, the paywall check, and the minimum-length guard) and feeds the text into the existing chunk_text -> synthesize -> write_episode flow.
  3. A small rss.py change so a text episode with no source url omits the "Original article" line instead of rendering a broken link.
  4. AGENTS.md documents the text mode and when to prefer it (paywalled content the user already receives in full).

No change to the cookie-authed /share flow, the rate limiter (a text share counts as one via="agent" episode against the same cap), the TTS synthesis, voices, or the v3.13 list endpoint.

3 · Request contract

POST /u/{secret}/episodes keeps its hand-parsed JSON body (a Pydantic model would 422 instead of the documented 400). The body is inspected in this order: 

POST {base}/u/<secret>/episodes
Content-Type: application/json

{
  "text":  "Full article or email body to narrate...",
  "title": "Hiking-sandal realness",
  "url":   "https://example.com/the-source"   // optional source link
}

Response: 202 Accepted   (identical shape to the url path)
{
  "slug": "k3kQ9rTzVx0",
  "status": "pending",
  "title": "Hiking-sandal realness",
  "status_url": "{base}/u/<secret>/episodes/k3kQ9rTzVx0",
  "feed_page": "{base}/u/<secret>",
  "remaining": 4
}

Mode selection and validation

  • Text mode is chosen when the body has a non-empty string text (non-empty after trimming whitespace). In text mode:
    • title is required: a non-empty string. Missing or empty title returns 400 {"error":"invalid_request"} with the message "Text requires a non-empty title."
    • url is optional. If present it must be http/https with a host, else 400 {"error":"invalid_url"} (the existing URL validation). It is used only as the episode's source link and is never fetched.
    • If len(text) > MAX_BODY_CHARS (500,000), return 400 {"error":"invalid_request"} with the message "Text too long: N characters (limit 500,000)." This rejects synchronously so an over-long paste never creates an episode or consumes a rate-limit share.
  • URL mode (unchanged): no text, but a string url. Existing behavior, including the async fetch and its paywall/length failures.
  • Neither a non-empty text nor a string url: 400 {"error":"invalid_request"}, message 'Body must include a string "url" or "text" field.'
  • Both text and url: text mode. The text is narrated; the url is only the source link (not fetched).

Validation (400) is checked before the rate-limit (429), which is checked before any episode is written, matching the current handler order. Unknown body fields are still ignored.

Text mode does no network I/O in the request: it does not call fetch_title (the title is supplied). The url path keeps its quick fetch_title call.

4 · Ingest path

ingest.process gains two keyword-only parameters, text and title, both defaulting to None: 

def process(url, secret, data_dir, slug=None, *, text=None, title=None):
  • Text branch (text is not None): the body is the supplied text; the final episode title is the supplied title; the source link is url or "". Skip fetch_article, the paywall declaration check, and the MIN_BODY_CHARS guard (the agent vouches for real content, and a legitimately short note should narrate).
  • URL branch (text is None): unchanged. Fetch, extract, apply the MIN_BODY_CHARS guard, source link is the url.
  • Shared tail: the MAX_BODY_CHARS ceiling is enforced on the resolved body in both branches (defensive in text mode, since the POST already rejected over-long text). Then chunk_text, update_pending_episode(total_chunks=...), synthesize, _excerpt description, and write_episode(title=..., source_url=...) run exactly as today. A failure still writes a failed episode via write_failed_episode(source_url=...).

spawn_ingest in app.py gains matching text/title keyword args and forwards them to the background ingest.process thread. The POST handler writes the pending episode with source_url = url or "", title, and via="agent" (as today), then spawns ingest with the text and title.

5 · Source link and RSS

Today rss._episode_description_html and _episode_description_text always render an "Original article:" line from the episode's url. A text episode may have no source url (stored as the empty string). The change: when the episode url is empty, omit the "Original article" line entirely (both the HTML and text descriptions); the "Generated with Feed Me" line stays. When a url is present (url mode, or text mode with an optional url), the line renders exactly as now. Storage writes url: "" for a text episode without a source link.

7 · AGENTS.md

Add a short "Narrate text directly" section after "Add an article" (and a pointer from the TL;DR). Content: when you already hold the full text of an article or email (for example a newsletter the user receives as a paying subscriber), POST {"text": "...", "title": "..."} instead of {"url": "..."} to narrate it directly and bypass the paywall a server-side fetch would hit. title is required; an optional url becomes the episode's source link. House style still applies: no em-dashes; keep the literal {base} token (plain .replace render). The existing test_agents_md_served_as_markdown assertions (the "5 episodes" cap, "Retry-After", no em-dash, no leftover {base}) must keep passing.

8 · Testing

TDD, no network, using the existing client / fake_http / fake_openai fixtures and the wire_fake_pipeline helper. New tests in tests/test_agent_api.py:

  • Text happy path: POST {"text","title"} with the pipeline wired synchronously yields a ready episode whose title is the supplied title and whose audio exists; no fake_http response is registered, proving no fetch occurred.
  • Source link: POST {"text","title","url"} stores the url; the rendered feed.xml contains the "Original article" link to that url, and the url was never fetched.
  • No source link: POST {"text","title"} (no url) produces a feed item with no "Original article" line, and the episode's stored url is the empty string.
  • Title required: POST {"text"} with no title (and with empty-string title) returns 400 invalid_request; no episode is created (welcome only).
  • Empty text: POST {"text": " ", "title": "x"} returns 400 invalid_request; no episode created.
  • Over-length text: POST text longer than MAX_BODY_CHARS returns 400 invalid_request with a "too long" message; no episode created and the rate-limit window is untouched.
  • Bad optional url: POST {"text","title","url":"ftp://x"} returns 400 invalid_url.
  • Neither field: POST {"foo":"bar"} returns 400 invalid_request (message mentions both url and text).
  • Counts toward cap: a text share decrements remaining and is visible in the v3.13 GET /episodes listing.
  • AGENTS.md: the rendered doc documents the text mode (a "Narrate text directly" section) and still passes the existing assertions and the em-dash guard.

9 · Out of scope

  • Text sharing from the iOS Shortcut / the cookie-authed /share path. This is agent-API only for now.
  • HTML sanitizing: text is treated as plain text to narrate. If the agent has HTML it strips markup before sending. Feed Me does not parse or clean it.
  • De-duplication of repeated text or url shares.
  • Any change to TTS chunking, voices, the rate cap value, or storage record shape beyond reusing the existing url/title fields.

10 · Acceptance criteria

  • POST with {"text","title"} narrates the supplied text with no network fetch and produces a normal ready episode.
  • title is required in text mode; missing/empty title, empty text, and over-MAX text each return a 400 {"error","message"} and create no episode.
  • An optional url renders as the episode's "Original article" link; with no url, that line is omitted (no broken link).
  • A text share counts as one agent share against the 5/24h cap and appears in the GET /episodes listing.
  • AGENTS.md documents the text mode with no em-dashes; the url path is unchanged.
  • Full suite green (uv run pytest); a CHANGELOG.md entry and a v3.14 tag accompany the change.
