Stats: Feeds & Shares Tables

Feed Me · 2026-06-02 · spec

The /admin/stats page currently shows aggregate counts plus a Top feeds (by shares) table and a Recently shared table, all drawn purely from the analytics events DB. This change adds a full Feeds table listing every feed on disk with its creation date and last-accessed time, folds the now-redundant Top feeds table into it as a shares column, and reorders the Recently shared table columns.

Privacy guarantee, unchanged. The Feeds table reads the filesystem (which is keyed by the raw secret) but renders only the one-way sha256(secret)[:12] hash. The raw secret is hashed inside the route loop and dropped before the template renders. It is never placed in template context, logged, or exposed. A test asserts the secret string is absent from the rendered page.

1 · Why

The owner wants a per-feed view on the stats page: the full list of feeds with when each was created and when it was last used, plus the recent shares in a clearer column order. The existing aggregate counts answer "how much" but not "which feeds, and how fresh." Today the page only surfaces the top 20 feeds by share count; there is no way to see every feed or its age.

2 · What we're building

  1. New Feeds table on /admin/stats: one row per feed dir on disk, columns Feed (hashed id) · Created · Last accessed · Shares, sorted by last-accessed descending.
  2. Drop the Top feeds (by shares) table: its data (per-feed share counts) becomes the Shares column of the Feeds table. The aggregate count cards (including Active feeds) stay.
  3. Reorder the Recently shared table columns to Feed · When · Article (still the most recent 25, unchanged limit).
  4. New helpers: storage.list_feeds() and analytics.feed_last_accessed(), combined in the admin_stats route.

3 · The Feeds table

  • Feed: the hashed id sha256(secret)[:12], rendered in a <code> tag like the other tables. Never the raw secret.
  • Created: the feed's created_at from settings.json, formatted %Y-%m-%d %H:%M UTC (matches the existing Recently shared format). If an old feed's settings.json lacks created_at, fall back to the file's mtime.
  • Last accessed: the newest analytics event timestamp for that feed hash, same UTC format. If the feed has no tracked events, show the literal word never (no em-dash, per project copy rule).
  • Shares: count of article_shared events for that feed hash (0 when none).
  • Sort: by last-accessed descending; feeds that have never been accessed (never) sort to the bottom.
What "last accessed" means. It is the newest analytics event for the feed: the owner opening their feed page (page_view / settings) or sharing an article (article_shared / feed_created). Podcast clients polling feed.xml and audio downloads are not tracked, so this reflects owner activity, not subscriber playback. The label stays "Last accessed" at the owner's request; this caveat documents the precise meaning.

4 · The Recently shared table

Today the columns are When · Feed · Article. Reorder to Feed · When · Article. No backend change: summary()["recent_shares"] already returns the most recent 25 (ORDER BY ts DESC LIMIT 25), which satisfies "show the past 25." This is purely a template column reorder.

5 · Data plumbing

Follows the existing layering: storage.py handles raw secrets, analytics.py only ever sees hashes, and app.py is the orchestrator that converts between them (exactly as _track() already does). storage.py does not import analytics.py; the hashing happens in the route.

Per-feed share counts already exist in summary()["top_feeds"], but that is capped at 20. The route needs a count for every feed, so add a small feed_share_counts(db_path) -> dict[str, int] to analytics.py (mirrors feed_last_accessed). summary() is left unchanged: top_feeds stays in the JSON export (a real consumer), it is just no longer rendered on the page.

The route

@app.get("/admin/stats", response_class=HTMLResponse)
def admin_stats(request: Request, token: str = ""):
    _check_stats_token(token)
    db = _analytics_db()
    last = analytics.feed_last_accessed(db)
    shares = analytics.feed_share_counts(db)
    feeds = []
    for f in storage.list_feeds(DATA_DIR):
        h = analytics.feed_hash(f["secret"])          # secret hashed here,
        ts = last.get(h)                              #   never put in the row
        feeds.append({
            "feed_hash": h,
            "created": _fmt_utc(f["created_at"]),
            "last_accessed_ts": ts,                   # for sorting; None sorts last
            "last_accessed": _fmt_utc(ts) if ts else None,  # None -> "never" in template
            "shares": shares.get(h, 0),
        })
    feeds.sort(key=lambda r: r["last_accessed_ts"] or 0, reverse=True)
    return templates.TemplateResponse(
        request, "admin_stats.html",
        {"s": analytics.summary(db), "feeds": feeds},
    )

Timestamps are formatted in the route (a small _fmt_utc helper, or reuse the existing UTC-format pattern) so the template just prints strings. Each row carries both last_accessed_ts (raw, for the sort) and last_accessed (formatted string, or None); the template renders never when it is None.

6 · Testing

TDD, following existing patterns (pytest, the client fixture points DATA_DIR at a tmp dir; fake_http/fake_openai for any ingest).

storage (tests/test_storage.py or test_app.py)

  • list_feeds returns one entry per feed dir with created_at.
  • list_feeds skips the _analytics dir and any dir without settings.json.
  • list_feeds falls back to file mtime when created_at is absent.

analytics (tests/test_analytics.py)

  • feed_last_accessed returns max ts per hash and ignores null feed_hash.
  • feed_share_counts counts only article_shared per hash.
  • Both return {} on an empty/missing DB without raising.

admin route (tests/test_app.py)

  • Privacy boundary (the test that matters): create a feed with a known secret via the client fixture, GET /admin/stats?token=…, assert the raw secret string is absent from the body and its feed_hash is present.
  • A feed that was created but never had an event renders never in Last accessed.
  • The Recently shared table renders columns in order Feed, When, Article.
  • Existing /admin/stats 404-without-token tests still pass.

7 · Out of scope

  • Tracking feed.xml / audio fetches. Would make "last accessed" reflect subscriber playback, but adds a tracked event on a hot, bot-heavy path. Not now.
  • Pagination / search on the Feeds table. The feed count is small; render all rows.
  • Per-feed episode counts or storage size. Only the requested Created / Last accessed (plus the folded-in Shares) columns.
  • Visual redesign of the stats page. Reuse the existing minimal table styling.

8 · Acceptance criteria

  • /admin/stats?token=… shows a Feeds table with one row per feed dir on disk, columns Feed (hashed) · Created · Last accessed · Shares.
  • A feed with no tracked events shows never for Last accessed; no em-dash appears anywhere in the template.
  • The raw secret never appears in the rendered page, the export, or logs; only the hash is shown.
  • The Top feeds (by shares) table is removed; its information lives in the Feeds table's Shares column.
  • The Recently shared table renders columns Feed · When · Article and still shows the most recent 25.
  • All existing tests plus the new storage/analytics/route tests pass; no new runtime dependency.
