Raise the Article Cap to 500k Characters

Feed Me · 2026-06-06 · spec

The 100k-character article cap (v1.7) bounded TTS cost at ~$1.50 per article. It also, silently, bounded TTS concurrency: synthesize() fires every chunk at the API in parallel, and the unbounded pool was justified by the cap (at most 25 chunks). Then a 265,012-character papal encyclical arrived via the agent API and failed with "Article too long." Owner decision: raise the cap to 500k characters rather than split long articles into parts. One article stays one episode.

The cap was load-bearing. At 500k characters an article is up to 125 chunks. Firing 125 simultaneous requests blows OpenAI's 50 req/min tier-1 limit for tts-1, so the cap raise must ship together with bounded TTS concurrency and explicit retry headroom. Raising the constant alone trades a clean "too long" failure for a flaky mid-synthesis one.

1. What ships

Three changes, all in ingest.py:

ChangeFromTo
MAX_BODY_CHARS 100_000 (~50 min audio, ~$1.50 max) 500_000 (~4h10m audio, ~$7.50 max)
synthesize() pool max_workers=len(chunks) (unbounded) max_workers=min(len(chunks), TTS_MAX_PARALLEL) with TTS_MAX_PARALLEL = 12
OpenAI client OpenAI() (SDK default: 2 retries) OpenAI(max_retries=5)
synthesize() output returns the full MP3 as bytes; caller writes the file streams batches to <slug>.mp3.tmp; write_episode atomic-renames it into place (see §3)
  • The "Article too long" error message interpolates the constant, so it updates itself to "limit: 500,000".
  • Articles up to ~48k characters (12 chunks or fewer, the typical case) get exactly today's behavior: every chunk in flight at once.
  • The stale comment justifying the unbounded pool ("worst-case 25 concurrent calls") is replaced by the reasoning in §2.

2. Rate limit reasoning

A pool of W workers issuing calls of duration T seconds settles at W·60/T requests per minute. With 12 workers that is under the 50 req/min tier-1 limit only when each tts-1 call takes at least ~15 seconds, and per-call latency for a 4k-char chunk is not reliably that slow. So the worker bound is not the correctness guarantee; it only keeps the burst sane and the thread count low.

The correctness guarantee is 429 retry. The OpenAI SDK retries 429s with exponential backoff and honors Retry-After; we raise max_retries from the default 2 to 5 so a 125-chunk article that runs hot for several consecutive minutes still drains. If a chunk exhausts its retries, the episode fails and the existing error path reports it; that is the same failure contract as today, just much less likely.

Why 12 and not 25 (the old worst case): 25 workers with fast calls could sustain ~150 req/min, hammering the retry path on every long article. 12 keeps the typical article unthrottled while making sustained overrun mild instead of 3x.

3. Memory: streamed synthesis (required, learned the hard way)

The first draft of this spec called memory a "known risk, accepted": the old synthesize() held every chunk's MP3 in a list, then b"".join(parts) allocated a second full copy. The first production run falsified "accepted" immediately: the 265k-char encyclical (69 chunks) OOM-killed the 1GB VM (anon-rss: 866MB), orphaning the episode as forever-pending. The arithmetic: a 4k-char chunk is ~4-5 minutes of speech, ~3-5MB of MP3, so 69 chunks is ~300MB held by the pool.map futures (all tasks are submitted up front; results are retained until consumed) plus ~300MB more for the join, plus lxml / readability / trafilatura trees from the 265k-char parse, plus the uvicorn baseline. At the 500k cap (125 chunks) the audio buffers alone are ~1.1GB: no VM size makes the accumulate-then-join design serve the stated range.

So synthesize(text, voice, out_path) now streams: it renders chunks in sequential batches of TTS_MAX_PARALLEL, appending each batch to out_path as it completes and releasing the bytes. Batch order preserves chunk order, and appending is byte-identical to the old join (tts-1 MP3 frames are self-contained). Peak audio memory is one batch, ~12 x 4MB = ~50MB, regardless of article length. Lazy iteration of one big pool.map would not achieve this (completed futures buffer their results); the sequential batches are the load-bearing part.

process() synthesizes to <slug>.mp3.tmp in the user dir (same filesystem, so the rename is atomic) and storage.write_episode(audio_path=...) renames it into place. A crash mid-synthesis leaves only a .tmp (cleaned up best-effort, invisible to list_episodes and the feed), never a ready episode with partial audio.

Still uncapped, still accepted: concurrent ingests (a thread per share). With streaming, N simultaneous max-length ingests cost ~N x 50MB, which the 1GB VM absorbs for any plausible N on a single-user app.

4. Testing

TDD, all against fake_http / fake_openai, no network:

  • Boundary test keeps testing the boundary. The existing too-long test builds a ~260k body, which the new cap would quietly turn into a "runs TTS" test. Rewrite it to derive its body size from ingest.MAX_BODY_CHARS so the post-extraction body exceeds the cap (extraction trims, so assert on extracted length, not raw HTML length). Asserts: status failed, "too long" in the error, zero TTS calls.
  • The encyclical case passes. A ~265k-char body (over the old cap, under the new one) processes end-to-end to a ready episode with concatenated audio.
  • Peak concurrency is bounded. Monkeypatch chunk_text to return 20+ chunks; a fake client counts in-flight calls under a lock (the OrderingFake pattern already in the file, plus small sleeps). Assert peak in-flight never exceeds TTS_MAX_PARALLEL and the written file's bytes stay in input order. Do not assert on the ThreadPoolExecutor constructor args; that is an implementation detail and is wrong for small articles anyway.
  • Streaming writes incrementally and fails clean. The synthesize tests assert against the file at out_path (the function no longer returns bytes). A fake whose create raises partway through must leave no final .mp3 and no leftover .mp3.tmp after process(), and the episode must be recorded as failed. A memory-bound assertion is not testable with tiny fake bytes; the batch structure is the guarantee (see §3) and prod verification watches RSS directly (§5).
  • write_episode accepts exactly one audio source. audio= bytes (existing behavior) or audio_path= (renames the temp file into place); passing both or neither raises ValueError.
  • Retry headroom is configured. ingest.openai_client.max_retries == 5, so a refactor cannot silently drop it back to the default.

5. Production verification

After deploy, re-share the encyclical through the agent API and poll its status URL. This is the empirical test of §2 and §3: watch the logs for 429s and OOM kills, watch process RSS during the run (the first attempt died at anon-rss: 866MB; the streamed version should stay flat), and check the finished episode's audio length is plausible (~2h12m for 265k chars) rather than truncated. If 429s show up in bulk, drop TTS_MAX_PARALLEL; the constants exist to be tuned. Note the encyclical exercises 69 chunks, not the 125-chunk ceiling; report accordingly.

7. Out of scope / future future

  • Multi-part splitting (Part 1 / Part 2 episodes for arbitrarily long texts): considered for this release, rejected in favor of the simpler cap raise.
  • A cap on concurrent ingests per machine.
  • Token-bucket request pacing (the bounded pool plus retries makes it unnecessary).
