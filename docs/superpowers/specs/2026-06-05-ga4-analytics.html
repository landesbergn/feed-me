Audience Analytics via GA4

Feed Me · 2026-06-05 · spec

The self-hosted analytics (v3.1) deliberately store no user agent, no IP-derived geography, and no referrer, so they cannot answer "who are my users and where do they come from." This release adds Google Analytics 4 alongside them: the owner's standard gtag.js snippet on the three user-facing pages, giving device, browser, city/state/country, and referrer reporting in the GA UI. The SQLite analytics and /admin/stats page are unchanged and remain the operational view.

The one hard constraint. The settings-page URL (/u/<secret>) is the account credential, and a stock GA install sends the full page URL and referrer to Google with every page view. Every gtag('config', ...) on a page whose URL or referrer can contain the secret must mask it. The secret must never reach Google in any field.

1. Why GA4

Alternatives considered: PostHog (preferred on features, but the free tier's single project is already used by noahlandesberg.com and sharing one project mixes audiences), Microsoft Clarity (free but replay-focused, new account, no session access from tooling), and enriching the homegrown SQLite store with a geo-IP lookup plus UA/referrer columns (most code to build and maintain by a wide margin). GA4 gives a dedicated free property, the requested data out of the box, and a familiar UI. Known trade-offs, accepted: adblockers hide a slice of the audience, standard reports lag up to a day or two, and visitor data lives with Google. The privacy posture of the v3.1 analytics ("no third party") is explicitly relaxed; the README must say so honestly.

2. What ships

  • One Jinja partial, templates/_ga.html, containing the owner's snippet (measurement ID G-MQ15LHLSBF, hardcoded; it is public in page source by nature). The partial takes one flag: whether to mask the page location.
  • Included by landing.html, share.html (unmasked location) and settings.html (masked location). Not included by admin_stats.html or any non-page response (RSS, audio, JSON).
  • The share page keeps its real URL including ?url=<article>: the shared article is content, not a credential, and seeing shared articles in GA is useful.
  • No env-var gating. The snippet renders always; tests never execute JS (TestClient renders HTML only), so the suite stays network-free. Local-dev page views are filterable in GA by hostname if they ever matter.

3. Secret masking

Two leak vectors, two masks, both inside the partial:

VectorWhere it leaksMask
page_location / page_path Settings page auto page_view carries /u/<secret> Config overrides: page_location: '<APP_BASE_URL>/u/_', page_path: '/u/_' (base URL from the app, so dev and prod both mask correctly)
page_referrer Navigating settings → share (or settings → landing) puts /u/<secret> in document.referrer on the next page On all three pages: if the referrer's path starts with /u/, override page_referrer with the masked form before config fires 
<!-- sketch of the partial's logic -->
var cfg = {};
try {
  var r = document.referrer && new URL(document.referrer);
  if (r && r.pathname.indexOf('/u/') === 0) {
    cfg.page_referrer = r.origin + '/u/_';
  }
} catch (e) {}
{% if ga_mask_location %}
cfg.page_location = '{{ base_url }}/u/_';
cfg.page_path = '/u/_';
{% endif %}
gtag('config', 'G-MQ15LHLSBF', cfg);

Everything else in the owner's snippet (the async loader, dataLayer bootstrap, gtag('js', new Date())) ships byte-for-byte. If GA is blocked or offline the page is unaffected: the loader is async and nothing else on the page depends on it.

4. What GA answers

QuestionGA report
Where do users come from?Acquisition → Traffic acquisition (referrer domain, channel)
Where are they located?Demographics → city / region / country
What devices / browsers?Tech → browser, OS, device category (from user agent)
Which pages get traffic?Engagement → Pages (landing vs /u/_ vs share)

Feed-level behavior (shares per feed, articles, episode status) stays on /admin/stats, which keeps its hashed-identity, no-PII design.

5. Testing

TDD, all string assertions against rendered templates (no network, no JS execution):

  • The snippet (googletagmanager.com/gtag/js?id=G-MQ15LHLSBF) renders on landing, settings, and share pages.
  • It does not render on /admin/stats.
  • The settings page contains the masked overrides (/u/_) and the raw secret appears nowhere inside the rendered <script> blocks.
  • The referrer-masking logic renders on all three pages.
  • Regression guard: rendering the settings page for a known secret asserts secret not in every gtag-related line (the secret legitimately appears elsewhere on the page, e.g. the feed URL box, so the assertion is scoped to the GA script block).

6. Documentation updates

  • README: the analytics section's "no third party" claim becomes a description of the two-tier setup: self-hosted SQLite for feed-level operational stats (still hash-only, no PII), GA4 for audience analytics (Google receives IP, user agent, referrer; never the feed secret).
  • CLAUDE.md gotcha: "GA's page_location / page_referrer must be masked on any page whose URL can contain /u/<secret>; the masking lives in templates/_ga.html. Never add the GA partial to a new secret-bearing page without it."

7. Out of scope / future future

  • Custom events (feed_created, article_shared with article domain) and user_id = feed_hash identity stitching.
  • Own-traffic exclusion (localStorage flag set by the admin page).
  • Server-side Measurement Protocol events for adblock-proof counting.
  • Consent banner / EU consent mode (personal project, revisit if audience changes).
