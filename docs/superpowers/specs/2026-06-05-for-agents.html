Spec · v3.6

For Agents

Feed Me · 2026-06-05 · spec

Let a user's AI agent (Claude Code, a cron script, any HTTP-speaking tool) add articles to their private feed. Two small JSON endpoints under the existing /u/<secret> path, an agent-facing API doc at /AGENTS.md (plus an /llms.txt pointer), and a "For agents" section on the feed page with a personalized copy-paste prompt. Inspired by usetranscribe.io's AGENTS.md and the "agents are the new mobile" thesis: a headless JSON surface for the product's core action.

No new credential. The feed secret already is the account; the agent endpoints authenticate solely by the secret in the URL path. Nothing new to mint, store, or rotate. The existing rotate flow invalidates a leaked URL.

1 · Why

Today the only way into a feed is the iOS share sheet, which requires a human holding a phone. Agents increasingly do the reading: they find articles during research, monitor topics overnight, and work where there is no share sheet. Giving them one documented JSON endpoint turns "send that to my feed" into a thing any agent can do with the feed URL the user already has. Transcribe's experience (53% of traffic from agents within days of removing auth friction) suggests the audience is real, and the integration cost here is small because the whole ingest pipeline already exists behind /share.

2 · What we're building

  1. POST /u/{secret}/episodes: JSON-in, JSON-out episode creation. Same internals as /share (quick title fetch, pending record, background ingest), minus the cookie and the HTML.
  2. GET /u/{secret}/episodes/{slug}: JSON status for polling, authed by the path secret (the existing /share/status is cookie-authed, so agents can't use it).
  3. GET /AGENTS.md (rendered Jinja template, served as text/markdown) and GET /llms.txt (a few plain-text lines pointing at /AGENTS.md).
  4. "For agents" section on the feed page (settings.html): a personalized prompt the user copies into their agent's instructions or memory.

3 · API contract

POST /u/{secret}/episodes

Body: {"url": "https://example.com/article"} with Content-Type: application/json. Unknown body fields are ignored (room for text, PDFs, or options later without breaking existing agents). URL validation matches /share: scheme must be http/https with a host.

Implementation note. The handler must take the raw Request and parse the JSON itself, not declare a Pydantic body model: FastAPI's automatic validation would reject malformed or missing-field bodies with its own 422 {"detail": […]}, breaking the 400 {"error": "invalid_request"} contract below. Don't "clean this up" into a model later.

On success, 202 Accepted:

{
  "slug": "k3kQ9rTzVx0",
  "status": "pending",
  "title": "The Article Title",        // null if the quick title fetch failed
  "status_url": "{base}/u/{secret}/episodes/k3kQ9rTzVx0",
  "feed_page": "{base}/u/{secret}",
  "remaining": 3                       // agent shares left in the rolling window
}

Internally: ingest.fetch_title(url), storage.write_pending_episode(..., via="agent"), spawn_ingest(...), analytics. Identical flow to share_route; the episode then lives, updates, and renders exactly like a Shortcut-shared one.

Errors are JSON with stable codes agents can branch on:

StatusBodyWhenRetry?
400{"error": "invalid_request", "message": …}Body isn't JSON or has no url fieldNo: fix the request
400{"error": "invalid_url", "message": …}URL isn't http/https with a hostNo: fix the URL
404{"error": "not_found", "message": …}No feed at that secretNo: check the feed URL with the user
429{"error": "rate_limited", "message": …} + Retry-After headerAgent cap reached (§4)Not before Retry-After; tell the user

Unlike the human /share path, an invalid URL writes no failed-episode record: the agent gets the error in the response, so there is nothing to surface on the feed page, and a buggy agent can't litter the feed. Ingest-level failures (paywalls, fetch errors) still produce a failed episode, reported through the status endpoint just as they appear on the feed page.

GET /u/{secret}/episodes/{slug}

200 with the episode's state, derived from storage.list_episodes (which already computes status from the record + mp3 presence): 

{
  "slug": "k3kQ9rTzVx0",
  "status": "pending" | "ready" | "failed",
  "title": "The Article Title",
  "ts": 1781234567,
  "total_chunks": 12,                  // present once ingest has chunked
  "error": null,                       // human-readable string when failed
  "audio_url": "{base}/u/{secret}/audio/k3kQ9rTzVx0.mp3"   // when ready
}

404 (not_found) for an unknown feed, an unknown slug, or a slug failing SLUG_RE. The welcome episode is reachable here like any other; no special casing.

Both routes return JSON only, never HTML, and never set or read cookies.

4 · Rate limiting

AGENT_DAILY_CAP = 5 episodes per feed per rolling 24 hours, counted at request time from the episode records themselves: entries from list_episodes where via == "agent" and ts > now - 86400. No new storage, no timezone math. The Shortcut path and the welcome episode never carry via, so human sharing is never throttled.

  • Failed agent episodes count toward the cap (they consumed a fetch and possibly TTS work; also prevents error-loop spam).
  • Rejected-before-write requests (400s) don't count; nothing was created.
  • 429 carries Retry-After: <seconds> computed as (oldest counted episode's ts + 86400) − now.
  • remaining in the 202 response is cap − count after the current share, so an agent can pace itself without a second call.

The check-then-write is racy (two simultaneous POSTs can both pass the count). Accepted: the worst case is one episode over cap, the product is single-user-per-feed scale, and the cap is a cost guard, not a security boundary.

5 · The agent doc

GET /AGENTS.md renders templates/agents.md with APP_BASE_URL so every example URL is absolute and correct per environment. Served as text/markdown; charset=utf-8. Modeled on Transcribe's AGENTS.md. Contents:

  1. What Feed Me is, one paragraph: articles in, narrated podcast episodes out, private per-user feeds.
  2. Auth: the user gives you their feed URL ({base}/u/<secret>). The secret in it is their entire account. Treat it like a password: never log it, never echo it into shared context, never post it anywhere public.
  3. Endpoints: the two routes from §3 with request/response examples, plus GET /u/{secret}/feed.xml as the read side.
  4. Errors: the table from §3, including which are permanent (don't retry) vs transient.
  5. Etiquette: share only what the user asked for; don't retry permanent errors; on 429 stop and tell the user; poll the status URL no faster than every few seconds; send a descriptive User-Agent.
  6. Rate limit: 5 episodes per feed per rolling 24h via this API; the user's phone sharing doesn't count against it.
  7. Examples: one curl, one short Python (httpx) snippet that shares and polls to completion.

GET /llms.txt returns a few plain-text lines: one sentence on what the service is, then "API documentation for agents: {base}/AGENTS.md".

House copy rules apply to both files: no em-dashes; the middot · is fine.

6 · Feed page section

A new "For agents" section on /u/{secret}, after the existing setup/voice sections, following the page's current section styling. Copy (final wording may be tuned during implementation, no em-dashes): 

For agents

Your AI agent can add articles to this feed. Copy this into your
agent's instructions or memory:

    I have a Feed Me podcast feed. To send an article to it, read
    https://feed-me.xyz/AGENTS.md and follow it. My feed page:
    https://feed-me.xyz/u/<secret>. Agents can add up to 5
    episodes per day.

Keep this private: that link is your whole account.

The block is personalized with the real feed URL (and APP_BASE_URL), shown in a copyable <pre>/text block consistent with how the page presents other copyable things.

7 · Storage & analytics changes

  • storage.write_pending_episode gains an optional via: str | None = None parameter; when set, the record stores "via": "agent". Absent means human (Shortcut or welcome). list_episodes already passes unknown keys through, and all episode consumers (rss, templates, status) read records as plain dicts, so the extra key is inert everywhere else.
  • via must survive finalization. Both finalization writers build fresh dicts today: write_episode (success) and write_failed_episode (ingest failure) overwrite the pending JSON with only title/url/ts(/error/description). Without a fix, via vanishes the moment an episode completes, silently turning the daily cap into a concurrency cap (a drip agent would never hit 5). Both functions must, when finalizing an existing slug, read the existing record and carry via forward. Targeted carry-over of exactly that key; the fresh-dict semantics otherwise stay (e.g. pending is still dropped).
  • Analytics article_shared props gain a via key on both paths: "agent" from the new endpoint, "shortcut" from share_route, so the split is unambiguous in /admin/export with zero admin-UI changes.
  • No User-Agent capture. The analytics spec (v3.1) promises user-agents are never stored; via already answers "agent or human". Storing agent UA strings is a separate owner decision, out of scope here (§10).

8 · Security

The load-bearing invariant: no ambient authority. The agent endpoints authenticate solely via the secret in the path and MUST NOT read the fm_session cookie. A cross-site request therefore gains nothing: to target a feed you need its secret, and anyone holding the secret already has the whole account. CSRF doesn't apply because no cookie-borne credential is honored. (CORS is a footnote: we add no CORS headers, so browser pages can't read responses either.)

  • Agent endpoints never call set_session_cookie; responses are cookie-free.
  • Unknown feed → 404 with a generic body, revealing nothing (matches the admin-route posture).
  • The raw secret keeps its existing rule: never logged, never in analytics (only feed_hash). It appears only in response URLs returned to the caller who already supplied it.
  • Worst-case TTS spend from a runaway agent is bounded by the cap: 5 episodes per feed per day.
  • AGENTS.md instructs agents to treat the feed URL as a password (defense in depth, §5).

9 · Testing

TDD, existing fixtures (client, fake_http, fake_openai); no network.

POST /u/{secret}/episodes

  • Happy path: 202; response has slug, status "pending", title, absolute status_url/feed_page, remaining 4; ingest runs (episode goes ready with the fake pipeline); the on-disk record still has via: "agent" after reaching ready (pins the finalization carry-over from §7, not just the pending write); article_shared event recorded with props.via == "agent".
  • Failed ingest keeps via: "agent" on the failed record (the write_failed_episode carry-over).
  • No/invalid JSON body and missing url → 400 invalid_request; bad scheme/host → 400 invalid_url; in both cases no episode file is written.
  • Unknown secret → 404 not_found.
  • No cookie involved: request with no cookie succeeds; response sets no cookie. The endpoint ignores a valid fm_session cookie for a different feed (path secret wins).

Rate limiting

  • 5 agent episodes in-window → 6th returns 429 with Retry-After; remaining decrements 4→0 across the first five. This test drives five real POSTs through the fake pipeline to completion (episodes reach ready), so it validates daily semantics, not concurrent-pending counting; a via-drop at finalization would fail it.
  • Agent episodes older than 24h don't count (write a record with an old ts).
  • Shortcut shares neither count toward nor are blocked by the cap: with 5 agent episodes in-window, GET /share still works.
  • Failed agent episodes count toward the cap.

GET /u/{secret}/episodes/{slug}

  • Pending → ready transition visible across the fake ingest; ready includes audio_url.
  • Failed episode: status "failed" with the error string.
  • Unknown slug, malformed slug, unknown secret → 404.

Docs routes & page

  • /AGENTS.md: 200, text/markdown, contains APP_BASE_URL-absolute URLs and the cap value; no em-dash character anywhere in the body.
  • /llms.txt: 200, plain text, points at /AGENTS.md.
  • Feed page: "For agents" section renders with the real feed URL inside the copy block.
  • Analytics: a Shortcut share's event now carries props.via == "shortcut".

10 · Out of scope

  • Text / PDF / non-URL content. The JSON body leaves room ({"text": …} later); v3.6 is URLs only. future
  • MCP server. Plain HTTP first; an MCP layer could wrap these same endpoints later. future
  • Storing agent User-Agent strings. Would reverse the analytics spec's "no user-agents" promise for one path; needs an explicit owner decision, and via already covers agent-vs-human.
  • Per-IP rate limiting. The per-feed cap bounds spend; feeds are unguessable, so unauthenticated spray isn't a cost vector.
  • JSON episode listing. Agents that want the catalog can read feed.xml; no need for a second list format yet.
  • Landing-page mention. Discovery is the feed page section + /llms.txt; marketing copy can come later.

11 · Acceptance criteria

  • An agent holding only the feed URL can create an episode with one POST and follow it to ready via the status URL, no cookie involved.
  • A 6th agent share inside 24h returns 429 + Retry-After while the iOS Shortcut keeps working uncapped.
  • /AGENTS.md and /llms.txt serve correct, environment-absolute documentation; an agent following only /AGENTS.md can complete the share-and-poll flow.
  • The feed page shows the personalized "For agents" prompt.
  • article_shared analytics distinguish via: "agent" / "shortcut"; no user-agent strings stored; raw secrets appear nowhere new.
  • Agent endpoints neither read nor set cookies.
  • No em-dashes in any new user-facing or agent-facing copy.
  • README route table updated; CHANGELOG.md gains a v3.6 entry; all existing tests plus the new ones pass.

Brainstormed via terminal Q&A on 2026-06-05. Inspired by usetranscribe.io/AGENTS.md and Gokul Rajaram's "agents are the new mobile" threads. Chose a JSON endpoint under /u/<secret> over extending GET /share (GET side effects misfire with agents and link-preview bots) and over an MCP server (over-engineering for v1; can wrap later). Secret-as-credential keeps the no-login identity model; a 5/day rolling cap (owner's number) bounds TTS spend; User-Agent capture deliberately deferred to preserve the analytics privacy promise.
